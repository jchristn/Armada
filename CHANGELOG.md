## Unreleased

### Captains list Evaluate action

- **Evaluate... in the captain row menu.** The Captains list Actions menu has an Evaluate... item (after View Tools, shown to global and tenant admins) that opens the same Evaluate dialog as the captain page. Submitting starts the run through `POST /api/v1/captains/{id}/evaluate` and opens `/captains/{id}?evaluationRun=<run id>` with a toast naming the run. No server change.

### Full Evaluate follow-up (model heterogeneity Phase 5, item 4)

- **Incomplete reports on the profile.** A cancelled or timed-out Full Evaluate (or one whose battery could not run) is now also recorded as an advisory model profile revision, marked `EvaluationIncomplete`. It never changes an earlier revision, never fills `measured`, is never preferred over a complete report, and observations never pool into it. Nothing reads it for routing. No migration.
- **`measured` block.** `GET /api/v1/model-profiles/{id}` and MCP `get_model_profile` return `Measured`: the counts from the latest complete Full report (run, revision and battery run ids, report time, packs, one count per probe kind, and per persona one count per pack with passed, failed, could not run, pending evaluation and attempted). Counts only, no derived scores; null until a complete report exists.
- **Dashboard Evaluate dialog.** The captain page's Full Evaluate control opens a dialog with depth (Full by default), the evaluator captain (idle captains, with a note when one shares the evaluated captain's model family), battery packs, personas and run count, and submits to `POST /api/v1/captains/{id}/evaluate`. The report view is unchanged. New client helper `listBatteryPacks`.
- **TUI Evaluate view.** The TUI captain page has an Evaluate action (`v`) with the same options, then a viewer that polls the run, shows its probe results and report, and cancels it with `c`.

## v1.2.0 (2026-10-29)

v1.2.0 adds the mission and voyage black box: every failure writes an entry that says where, how and why it
failed, which missions and files it collided with, and how to recover, with a FIX THIS brief for any coding agent (see
the first section below). It also adds pi (pi.dev) as a first-class captain runtime, with Armada MCP, Approve in Armada and Refuse support (see
its section below). The rest of the release is about model evaluation: knowing how well each model does the work
it is given, and handing work to it in a form it can use. Every stage attempt is recorded as a stage outcome with its provenance (runtime version, model
digest, escalation record) and a suspected cause; Quick probes give a captain or model endpoint a probe-only
**Evaluate**; the fixture battery runs data-defined task packs (starting with C#) through real dispatch; and handoffs
are delivered with their reader in mind. The release also improves captain usage visibility and management, and adds
mobile interfaces for the new surfaces. Since v1.1.0 was cut it also includes the `ExcludeReviewAuthorsFromJudge`
setting, Quick probes, and the fixture battery with its C# pack. Schema migrations 96 to 106 apply automatically at
startup; see [UPGRADING.md](docs/UPGRADING.md#v110-to-v120).

### Worker eligibility envelope (model heterogeneity Phase 6, item 1)

- **Vessel default.** A vessel may carry a default `WorkerEnvelope` (`maxFiles`, `maxSteps`, `minServedContextTokens`, `requiredTools` of `tools`/`mcp`), set through REST vessel create/update, WebSocket `create_vessel`/`update_vessel`, MCP `add_vessel`/`update_vessel` (`workerEnvelope`; `{}` clears it, omitted keeps it) and the dashboard and TUI vessel forms; `get_vessel` returns it. Out-of-range values or unknown tools are rejected (`400`, MCP `InvalidArgument`). No envelope is the default, so routing is unchanged until a vessel sets one. Stored in a new column (migration 110 on SQLite, PostgreSQL, SQL Server and MySQL).
- **Missions may only tighten it.** A mission may carry a tighter envelope (fewer files or steps, a larger context minimum, more required tools). REST dispatch rejects a loosened envelope with `400`; a `workerEnvelope` on a mission in the Architect's plan is clamped to the vessel default and an event `mission.worker_envelope_clamped` is recorded.
- **Dispatch enforces it for the Worker stage.** Only captains whose model profile records at least the minimum served context and the required tools are eligible; a captain with no profile, or a profile missing a needed field, is excluded. When no idle eligible captain exists, the mission escalates to a stronger compatible captain within the Worker persona's allowed captains; when none exists it stays Pending with a visible reason. Each decision (which captains were excluded and why) is recorded as event `mission.worker_envelope`, shown in the mission timeline and the black box.
- **Prompts.** New prompt template placeholder `{WorkerEnvelope}`, used in the Architect and Judge templates, renders a short description of the envelope (empty when none). Listed in the dashboard and TUI placeholder panels.
- **Mission update and creation.** REST `PUT /api/v1/missions/{id}` and MCP/WebSocket `update_mission` set or clear a mission's envelope (`{}` clears, omitted keeps) with the dispatch validation (`400` / `InvalidArgument` when invalid or looser than the vessel default); a change is only accepted while the mission is Pending, or Assigned and not started (`409` / `Conflict` otherwise). MCP `create_mission` takes an optional `workerEnvelope` and `armada mission create` takes `--max-files`, `--max-steps`, `--min-context-tokens` and `--require-tool`.
- **Customized templates.** An Architect or Judge template customized before `{WorkerEnvelope}` existed is not rewritten; when it lacks the placeholder and an envelope applies, the rendered envelope section is appended after it and a warning is logged once per template.

### Landing verification

- Landing verification for the Armada repository now runs the smoke tests (`dotnet test "src/Test.Smoke/Test.Smoke.csproj" -c Release -f net10.0`) instead of the long `src/Test.Automated` suite list, which was being killed (exit 143) and blocking landings.

### Full Evaluate (model heterogeneity Phase 5, item 4)

- **`evaluate_captain` and `POST /api/v1/captains/{id}/evaluate` (and `/model-endpoints/{id}/evaluate`) accept depth `Full`.** Full runs the Quick probes, then a fixture battery run for the candidate (packs default to those matching the languages of the tenant's repositories; personas default to every persona the captain is allowed), then an evaluator captain grades the battery attempts that need a subjective grade and writes strengths and weaknesses from the mechanical counts. Parameters: `evaluatorCaptainId`, `packs`, `personas`, `runCount`. Quick stays the default. A Full Evaluate of a model endpoint needs an admin (`403` otherwise).
- **Evaluator selection.** By default the highest-tier idle captain of a different model family from the candidate; a same-family evaluator only when no other is idle, with a warning in the report; with none, the mechanical report is still produced and the narrative is `Skipped` with the reason.
- **Counts are the source of truth.** The report (`ModelProbeRun.Report`) holds per-persona counts (total and per task) and probe counts. Every count the evaluator's narrative cites must match them; a reply that does not parse or cites a wrong count is `Rejected` with the reason and the mechanical report is kept. The run does not fail.
- **Advisory profile update.** A complete Full report is recorded as a new immutable model profile revision (`EvaluationRunId`, `EvaluationReport`, migration 109), marked compatible with the revision it was recorded on so the scorecard pools them. Nothing changes routing, persona captain lists or prompts.
- **Isolation, budget and limits.** Battery missions are flagged `IsEvaluation`, so they never count in scorecards or alerts. New settings `evaluation.fullRunTokenBudget` (default 3,000,000 estimated battery tokens, within the daily evaluation budgets) and `evaluation.fullRunTimeoutMinutes` (default 720). A Full run holds the evaluation slot of its inference host for its whole run, so models sharing one machine are evaluated one at a time.
- **Cancel.** `POST /api/v1/model-probe-runs/{id}/cancel` and MCP `cancel_model_probe_run` (admins) stop a Quick or Full run; a cancelled or timed-out Full run ends `Cancelled` with a partial report marked incomplete, and its open battery mission is cancelled, releasing its dock and captain. New run status `Cancelled` (also on battery runs).
- **Dashboard.** The captain page and the endpoint health dialog have a Full Evaluate button next to Evaluate, a Cancel button while a run is going, and show the Full report (completeness, evaluator, warnings, per-persona counts, strengths, weaknesses, observed problems, how to work with the model, or why the narrative was skipped or rejected). Full uses the server defaults there; the parameters are REST and MCP only.

### Model alerts (model heterogeneity Phase 5, item 3)

- Scorecard alerts as inbox items (kind `model_alert`, admins only) with suggested actions; advisory, no automatic changes. A periodic pass (`ModelAlerts.IntervalMinutes`, default 60; `ModelAlerts.Enabled`) and on-demand evaluation check every (model profile, persona) with recent production attempts against Decision 13's thresholds (first pass below 50% over 8+ missions, 3 escalations away in a row, protocol repairs above 30% over 8+ attempts, tokens per accepted result above 2x the persona median across other profiles with 5+ accepted results on each side), with per-persona overrides in `ModelAlerts.Thresholds`. Unavailable metrics make a rule inactive and are reported.
- One alert per (profile, revision group, persona, vessel or all, rule), stored in `model_alerts` (migration 108 on SQLite, PostgreSQL, SQL Server and MySQL), kept while the condition holds, resolved when it clears and reopened when it returns.
- Suggested actions, applied only on request and recorded on the alert: move down in the persona's priorities, remove from the persona, re-evaluate (Quick Evaluate), ignore for N days (default 7). The compact template is listed as unavailable (no prompt variant per profile and persona).
- REST `/api/v1/model-alerts` (list, enumerate, get, evaluate, thresholds get/put, apply, ignore), MCP `list_model_alerts`, `get_model_alert`, `evaluate_model_alerts`, `get_model_alert_thresholds`, `update_model_alert_thresholds`, `apply_model_alert_action`, `ignore_model_alert`, and `Armada.Client` methods. The scorecard adds `escalations.inARow`.
- Optional push (`ModelAlerts.PushEnabled`, default false) under the new push category `ModelAlert`.

### Model profiles (model heterogeneity Phase 5, item 1)

- New advisory **model profile** entity (`mdl_` prefix): the model as served, identified by runtime, provider, model and
  served context, shared by every captain and Harbor that runs it, with editable capabilities (`ToolsAvailable`,
  `McpAvailable`), explicit rendering overrides (`Template`, `RepeatContractAtEnd`, `MaxFilesPerMission`) and notes.
  Profiles do not set `Captain.Tier` and do not change routing or dispatch.
- Immutable **revisions** (`mdv_` prefix) record the runtime version, model digest, sampling, tool configuration and first
  seen time. A new runtime major version, a new model digest or a change in sampling starts a new revision; a runtime
  minor or patch release pools into the current one; a change in served context is a new profile. Administrators can
  mark revisions compatible; revisions are never edited.
- Armada finds or creates the profile and revision whenever it records a captain's runtime and model (every stage
  outcome and every Quick Evaluate run), best effort, and sets the new server-owned `Captain.ModelProfileId`. Vendor CLI
  captains are profiled too.
- REST: `GET /api/v1/model-profiles`, `POST /api/v1/model-profiles/enumerate`, `GET /api/v1/model-profiles/{id}`,
  `PUT /api/v1/model-profiles/{id}` and `PUT /api/v1/model-profiles/{id}/revisions/{revisionId}/compatible-with`. MCP:
  `get_model_profile` and `list_model_profiles`. .NET client: `ListModelProfilesAsync`, `EnumerateModelProfilesAsync`,
  `GetModelProfileAsync`, `UpdateModelProfileAsync`, `SetModelProfileRevisionCompatibilityAsync`.
- Schema migration 107 adds `model_profiles`, `model_profile_revisions`, `model_profile_revision_compat` and
  `captains.model_profile_id` on SQLite, PostgreSQL, SQL Server and MySQL (additive).

### Model scorecard (model heterogeneity Phase 5, item 2)

- New read-only scorecard per (model profile, persona), optionally per vessel, computed from existing stage outcomes,
  token usage and timing over the last 30 days or 50 missions, whichever is smaller (both configurable): first-pass
  success, accepted results, stage-check status counts (skipped by reason), Judge verdicts on the profile's work,
  protocol repairs and repairs that ran out, tool failures, resumes in place and stalls, escalations away and what
  followed, suspected causes (Unknown and Mixed as their own buckets), and tokens and wall time per accepted result
  summed over every attempt that led to it. Every rate is a count of a denominator with a 95% Wilson interval; metrics
  Armada does not record (finding categories, tool failure kinds, recovered stalls) are returned as unavailable with the
  reason. Revisions are shown separately unless marked compatible. The attribution rules applied (evaluation and battery
  missions, NotTheModel, Infra, OperatorAction, runtime environment, unsettled, other stages, Judge verdicts on other
  captains' work) are listed with how many items each removed. No routing or captain change and no schema migration.
- REST `GET /api/v1/model-profiles/{id}/scorecard` (query `persona`, `vesselId`, `windowDays`, `windowMissions`), MCP
  `get_model_scorecard` (Ask read-only), .NET client `GetModelScorecardAsync`.

### Mission and voyage black box

Every mission or voyage failure, of any kind and including landing failures, now writes a black box entry at the
moment of failure: where it failed (phase, step, host, code site), how (exception, exit code, failing command, git
error), status before and after, why (classified cause with rule ids and confidence), conflicting missions with the
files and directories they collided on, the configuration in effect and what would have prevented the failure, Armada
behavior changes that could address it, and ranked recovery paths with exact commands. Each entry renders a FIX THIS
brief to paste into any coding agent. Entries are stored in the database by default (BLOBs indexed by mission,
voyage, vessel, captain and other ids), or on disk, S3 and S3-compatible stores, Azure Blob, Google Cloud Storage,
CIFS or NFS, with configurable retention and garbage collection. Available in the dashboard, the VS Code extension,
the mobile app, REST, MCP, WebSocket and Ask Armada (read tools); the TUI Failure tab and Helm `armada blackbox`
commands arrive with their own changes. Schema migrations 103 and 104 apply at startup. See
[docs/BLACKBOX.md](docs/BLACKBOX.md) and [docs/BLACKBOX_SCHEMA.md](docs/BLACKBOX_SCHEMA.md).

- Capture: every failure write (dispatch, provision, execution, completion, review, handoff, landing, merge queue, recovery, voyage settlement, operator transitions and vessel deletion) records an entry after the row update, within `blackBox.captureTimeoutMs` (2000), and never breaks failure handling. Each attempt keeps its own entry; `Mission.LastBlackBoxEntryId` and `Voyage.LastBlackBoxEntryId` point at the current one, and clearing a mission's failure reason no longer loses the evidence. A sweeper captures any failure without an entry (`CaptureMode` Sweeper), and `POST /api/v1/blackbox/backfill` captures failures from before the upgrade (Backfill). Every capture emits `mission.status_changed` with `PreviousStatus`, and missions record their start commit (`Mission.StartCommit`) at every provision.
- Enrichment runs git on the host that owns the dock (the Admiral, or a Harbor over the Harbor link): worktree and branch state, `git status` of the worktree and target, target commits since the start commit, conflict attribution by `Armada-Mission-Id` trailer, concurrent missions on the same files, directory roll-ups, earlier attempts and rescues, evidence objects (agent output, mission log tail, diff and diff stat, check and verification output, merge entry, events) and the effective configuration with the source of every value.
- Every black box entry is analyzed by a versioned rule catalog (66 rules, `BBX-LAND-001` to `BBX-UNKNOWN-001`, every failure phase covered): why findings with confidence and evidence, configuration recommendations, Armada improvement hypotheses with source pointers, ranked recovery paths with MCP, REST and CLI commands, a weighted triage verdict (a tie reports Unknown and both candidates) and a plain-language summary. Entries analyzed with older rules are re-analyzed in the background.
- Recovery paths and configuration recommendations run only the action recorded in the entry: a dry run returns the plan and a 10-minute, single-use confirm token bound to the entry, the path and the mission version; the confirmed run re-checks the mission, refuses data-loss paths without `acknowledgeDataLoss`, authorizes every step as if the caller called the tool directly, annotates the entry and emits `blackbox.recovery_run`.
- The effective configuration in an entry names the source of every value (mission, voyage, vessel, workflow profile, captain, persona, global or default), with the landing handler's precedence.
- With `blackBox.summaryEndpointId` set, a model endpoint writes the entry summary (labeled model-written); any failure keeps the rules summary.
- Every entry has one FIX THIS brief (`brief.md`), written for a coding agent: it asks the reader to triage the failure (UserConfig, MissionBrief, Transient, ArmadaDefect or External) and then fix it with evidence, and every surface serves it. The maintainer bundle groups up to 50 entries by fingerprint and asks for ranked Armada mission briefs; fingerprint trends count a failure mode per Armada version; entries export as sanitized regression fixtures.
- `update_vessel` accepts `landingMode` (or `Default` to clear the vessel's override).
- Resilience bias: the black box has a strong bias toward finding problems within Armada's own handoff and landing. In the handoff and landing scope (phases Handoff, Landing, MergeQueue, Recovery and Provision, output contract parsing, check harness errors, a false scope check, and dock, worktree, branch and target-sync facts of any phase) the advisor adds the `BBX-PRIOR-ARMADA` vote for ArmadaDefect, so ArmadaDefect wins unless a rule has strong, specific evidence for another verdict; a verdict that rests on the prior alone is a suspected Armada defect with Low confidence. Outside the scope triage is unchanged.
- Every analyzed entry has an Armada resilience section (`analysis.resilience`): whether Armada could have healed the failure by itself and how, the detection gap and the invariant that should hold, code pointers into the handoff and landing services at the build commit, proposed Armada changes as mission briefs ranked by impact (severity escalates with recurrence: once Medium, 3 or more High, 5 or more or across 2 Armada versions Critical), the regression test, and the recoveries Armada already attempted. Rules version 2 adds resilience content to every handoff and landing rule and 24 new rules (moved targets, rejected pushes, credentials, pull requests, missing branches, exhausted retries and deferrals, unpublished ancestry, stale merge entries, queue repository and push failures, check harness errors and flakes, stale worktrees, branch and start commit provisioning, vanished docks, plan parsing, stage hardening, integration barriers, unconfirmed stops, orphaned exits, missing merge handoffs, exhausted redispatches). Existing entries are re-analyzed in the background.
- In scope the enrichment records the handoff and landing trail (`record.handoff`, `evidence/handoff-timeline.json`): the ordered completion, stage check, handoff, landing, retry, deferral and reconcile steps, the automatic recoveries and their outcomes, dock and lease transitions and target movement.
- The brief puts `## Armada resilience` right after the Summary and, in scope, asks the reader to look for the Armada fix (with a test) first; the summary leads with "Armada's landing could not ...; Armada could have ..."; the model-written summary and the Ask Armada guidance carry the same bias, and Ask offers Draft an Armada fix mission from the top proposed change.
- Armada resilience gaps: `POST /api/v1/blackbox/resilience-gaps/enumerate`, MCP `list_blackbox_resilience_gaps`, `ArmadaClient.EnumerateBlackBoxResilienceGapsAsync` and `armada blackbox gaps` list the handoff and landing failure modes triaged ArmadaDefect, grouped by fingerprint with occurrences, Armada versions and severity; `list_blackbox_entries` and the enumerate route take `resilienceScope`; `get_blackbox`'s summary carries the self-healable verdict, detection gap and top proposed change; `read_blackbox_section` reads `Resilience` and `Handoff`. The maintainer bundle defaults to the resilience gaps (`allFailures` for every failure), ranks groups by severity and recurrence, carries each group's proposed Armada changes and regression tests and asks for Armada missions.
- The dashboard panel, TUI, mobile app, VS Code extension and `armada blackbox show` show the Armada resilience section with a Suspected Armada defect marker and a Draft Armada fix mission action; the dashboard Black Box tab and the TUI have an Armada resilience gaps view.
- Objects: `record.json` (versioned, JSON Schema in `docs/blackbox-record.schema.json`), `brief.md` (the FIX THIS brief) and `evidence/*`, all redacted (registered secrets, private keys, authorization headers, credentials in URLs, GitHub, Anthropic, OpenAI, AWS, Azure, Google and Slack tokens, JWTs, secret pairs) and bounded (record 256 KB, briefs 40 KB, evidence `maxEvidenceObjectBytes`).

### Black box prevention, forensics and operations

- Dispatch warns about overlapping work: a mission's likely files (its scoped-files directive and the repository paths its brief names that exist in the vessel) are compared with the vessel's active missions, black box conflict hotspots and reserved directories, and the warnings come back as `OverlapWarnings` on REST `POST /api/v1/missions` and `POST /api/v1/voyages` and MCP `create_mission` and `dispatch`. `POST /api/v1/vessels/{id}/overlap-preview` (MCP `preview_mission_overlap`) shows the same before dispatching.
- `Vessel.SerializeOverlappingMissions` (default false; REST, `add_vessel`, `update_vessel`) chains a dispatched mission after the overlapping active mission with `DependsOnMissionId`; an explicit dependency is never replaced.
- Soft directory reservations: an active mission's scoped files in a directory the black box marks hot (`blackBox.hotspotReservationThreshold`, default 3, 0 off) reserve it; a second mission there is warned or chained. `GET /api/v1/vessels/{id}/reservations`, MCP `list_vessel_reservations`.
- The brief linter flags dependency language without `dependsOnMissionId`, verification-only briefs likely to fail as NoOp, host and parent-relative paths, and paths outside the vessel; dispatch returns the findings as `BriefLintWarnings` and never blocks. `POST /api/v1/missions/lint-brief`, MCP `lint_mission_brief`.
- The configuration doctor lists the recommendations that recur across a vessel's black box entries (count, first and last seen, an example entry): `GET /api/v1/vessels/{id}/blackbox-doctor`, MCP `get_vessel_blackbox_doctor`.
- Attempt diff (`GET /api/v1/blackbox/{id}/diff/{otherId}`, MCP `diff_blackbox_entries`), combined timeline across the entry, mission, dock, merge entry, captain and Harbor link (`GET /api/v1/blackbox/{id}/timeline`, MCP `get_blackbox_timeline`) and the voyage cascade graph (`GET /api/v1/voyages/{id}/blackbox/cascade`, MCP `get_voyage_blackbox_cascade`).
- The success flight recorder keeps a minimal record of each successful landing for `blackBox.successRetentionDays` (default 7, 0 off); a failure's record lists nearby successes on the same vessel that touched the same files (`Related.NearbySuccesses`, `GET /api/v1/blackbox/{id}/nearby-successes`, MCP `list_blackbox_nearby_successes`).
- Recovery paths link to runbooks tagged `blackbox: <path, rule, step or kind>` and a confirmed run starts the runbook instead of the tool steps. Every confirmed recovery run is tracked until the mission's next terminal status; per-path success rates (`GET /api/v1/blackbox/recovery-stats`, MCP `get_blackbox_recovery_stats`) break ties between equally weighted paths.
- New tables `blackbox_successes` and `blackbox_recovery_outcomes` and the column `vessels.serialize_overlapping_missions` (migrations 105 and 106, every provider); `Armada.Client` gains the matching methods.

### Black box evidence fixes

- A verified fast-forward into a dirty target checkout reports the checkout's real `git status --porcelain` paths (tracked and untracked) in `GitDirtyCheckoutException.ModifiedPaths`, instead of parsing a sentence into a garbage path.
- `retry_landing` lists conflicted files from the worktree where the merge ran (the dock worktree, then the target checkout), and from the conflicted files a merge read before it aborted, instead of from the owning repository, where the list was nearly always empty.
- The merge queue reads the conflicted files of a failed merge before aborting it and names them in the entry's output and the mission's failure reason.
- The merge queue classifies a failed entry by the step that failed: a real merge conflict is `LandingConflict`, a landing check that ran and failed is `TestFail` (`Timeout` when it ran out of time), and an unresolvable repository, a failed fetch or worktree, a check that could not run or rewrote the commit, and a refused push are `Infra`. Every merge queue failure was `LandingConflict` before, so non-conflict failures were auto-rescued. The structured facts (`MergeQueueFailure`: step, kind, conflicted files, target commit) are the Payload of the `mission.landing_failed` event the queue records; landing checks that do not pass raise `LandingVerificationException` with the command, exit code and commit.
- `mission.landing_target_advanced` carries a payload (`LandingTargetAdvancedPayload`): the dock head `Before` and `After` integrating the target, the target branch, and the remote and local target tips it integrated against.
- Every mission failure write records a `FailureKind`: a stranded landing handoff (`LandingConflict` for a real conflict, otherwise `Infra`), a lost merge queue handoff, an unverified orphan exit, a stop or recall the owning host never confirmed, a landing that was not attempted, and an unresolvable retry repository are `Infra`; missions cancelled because their vessel was deleted are `OperatorAction`. A kindless `LandingFailed` mission was classified as a landing conflict and auto-rescued.
- `maxLandingRetries` (default 3) now limits automatic retries of a landing deferred on a dirty checkout: each deferral is retried at most that many times (recorded as `mission.landing_auto_retry`), then `mission.landing_retries_exhausted` is recorded once and the landing waits for a manual retry; 0 disables automatic retries. The setting was never read before.

### Harbor and Helm packaging

- macOS Harbor bundles store the pi permission-gate extension in `Contents/Resources/Pi`, and pi resolves it there as well as beside portable binaries. This prevents ARM64 code signing from treating TypeScript resources as unsigned nested code. The DMG verifier checks the resource layout.
- After building and verifying both Harbor DMGs, `build-harbor-app.sh` installs the native app into `~/Applications`, staging and signature-checking a fresh bundle before replacement. `--no-install` opts out, and `--no-build` remains verification-only.
- Helm's NuGet tool package preserves battery fixture `.gitignore` and `.gitattributes` files instead of excluding them with NU5119 warnings. Installer verification checks every packaged framework for those files.

### Landing failure prevention

- Every dashboard and TUI delete, bulk delete and purge now shows a progress modal (for example "Deleting vessel" or "Deleting 12 missions": "This may take some time while related records are cleaned up.") that stays up until the server answers, cannot be dismissed while pending, and offers Retry and Dismiss if the delete fails. Duplicate submissions are ignored. Ask Armada uses the same shared dialog.
- Infra landing failures show Retry Landing next to the full failure reason on the mission page, and Needs You shows landing-failure reasons preformatted with a one-click Retry Landing.
- Docks with unlanded work (WorkProduced, Testing, Review, Verifying, PullRequestOpen, LandingFailed, or a queued merge entry) are no longer reclaimed unless the caller gives an explicit force reason. Every reclaim and refusal is recorded as `dock.reclaimed` / `dock.reclaim_refused` with the caller and mission status.
- Landing recreates a missing mission dock from its branch before running git. If it cannot, the mission fails as `Infra` naming the missing path and branch instead of a misleading `LandingConflict`. `retry_landing` also recreates a missing dock.
- Only a real git merge conflict (`GitMergeConflictException`) is classified `LandingConflict`. Git failing to start, refused pushes and other landing errors are `Infra`, so they no longer trigger autonomous rescues.
- A landing-integrity health phase repairs missing docks of unlanded missions (`dock.repaired`) and retries LocalMerge landings deferred on a dirty checkout once it is clean, until the new `landingDeferralDeadlineHours` setting (default 24, 0 disables).
- MergeAndPush records `mission.checkout_sync_skipped` when the developer checkout cannot be fast-forwarded after a landing; the landing still succeeds. Completion checks that the mission branch holds the produced commit (`mission.branch_verified` / `mission.branch_unverified`).
- Rescues for a mission that left a commit integrate that commit instead of re-implementing it, and no rescue is created while another active mission already names the failed mission or its commit.
- LandingFailed missions whose work already reached `origin/<default branch>` are completed automatically on each health check when proven: the mission's commit is an ancestor, or a commit on that branch carries its `Armada-Mission-Id` trailer. Each check is bounded, fetches each vessel at most once, works with Harbor-hosted vessels, and skips repositories it cannot reach. A `mission.landing_reconciled` event records the evidence. `LandingFailed -> Complete` is now a legal transition.
- A captain of any persona can end with `[ARMADA:STAGE-OUTCOME] BLOCKED` (or report `[ARMADA:MESSAGE] BLOCKED: ...`) plus a reason. Outside verifier stages, a blocked run with no work fails immediately with the new failure kind `Blocked` and the reason "Captain reported BLOCKED: ...", instead of being re-dispatched and failed as NoOp. A `mission.blocked_by_captain` event is recorded, and a new built-in failure-cause rule "Captain reported blocked" classifies it as not the model's failure. The unfinished-completion reason says "the model is stopping mid-task" only when the output had no result line and no blocking message.
- Fixed false "modified files outside its scoped file list" failures: host commands return git output unchanged (no extra trailing newline after the last NUL), the -z parsers ignore newline-only fields, and a bare file name in a "Touch only" directive matches that file in any directory. A scope failure never lists an empty path.
- Stage-check failures sent back to a captain keep the head and tail of the output plus a "Failing tests" section listing failing tests and compiler errors, so the failing test name is no longer cut off.
- Stopping a captain (stop_captain, stop_all, REST, WebSocket, dashboard) now cancels its mission instead of failing it. The reason records who stopped it, how and when, a `mission.stopped_by_operator` event is emitted, and uncommitted work is committed as a WIP commit on the mission branch and pushed before the dock is reclaimed. Operator stops recorded as Failed by earlier versions no longer appear in the inbox failure feed or count toward vessel mission-failure health.
### Bounded enumeration: shared contract (breaking)

- No REST route or MCP tool returns, embeds, or echoes an unbounded collection any more (docs/ENUMERATION.md). Stored collections are read one page at a time (`EnumerationQuery` to `EnumerationResult<T>`: default page size 10, 1 to 1000, exact `TotalRecords`, id tie-break), cut in the data source in all four database providers. Growing children that used to be embedded in a parent read (voyage missions, fleet vessels, status voyages, transcripts, tracked work, dependencies, cleanup resources, battery results, fleet action run targets) are counts on the parent plus their own paged enumeration.
- Lists that are not stored rows have limits in `CollectionLimits`: 1000 ids or keys per request, 256 entries per configuration list or dictionary stored on an entity, 1000 linked ids, 1000 summary buckets. Every collection property of a response model declares its limit with `[CollectionBound]`, and write paths call `CollectionBounds.Validate`. Exceeding a limit is a REST 400 with `Data.Code` `CollectionLimitExceeded` (`Field`, `Limit`, `Actual`), MCP and WebSocket `InvalidArgument` with `Code` `CollectionLimitExceeded`; nothing is truncated silently.
- The `E2E.ResponseShape` guard fails for an undeclared collection property reachable from a response, and for any array in a live REST or MCP response that is neither a page's `Objects` nor a declared bounded property within its limit.

- **One stage outcome per attempt.** When Armada handles a captain's exit it now stores a `StageOutcome` (`sto_` ids, table `stage_outcomes`, migration 92 on all four databases): the mission, voyage, vessel, captain, persona, attempt number and rework round; the runtime, model, provider, endpoint, Harbor, context size, sampling, tool settings, reasoning effort, prompt version and Armada version; the exit code, runtime failure kind, stage-check status and reason, failure kind and reason; what Armada did next (`Completed`, `Relaunched`, `OutputRepair`, `Escalated` with the next captain, `Failed`, `Interrupted`, `Cancelled`); and for a Judge, its verdict and the mission it reviewed. Recording never disturbs exit handling: a storage error is logged and skipped.
- **Suspected cause from editable rules.** Each attempt that fell short gets a suspected cause (`Protocol`, `InstructionFollowing`, `ToolUse`, `Context`, `Capability`, `NotTheModel`, `Unknown`, `Mixed`) from the first matching enabled `FailureCauseRule` (`fcr_` ids, table `failure_cause_rules`), ordered by priority then name. Rules match on persona, runtime, failure kind, runtime failure kind, stage-check status and reason, disposition and a failure-reason pattern (bounded by a 250 ms timeout). Thirteen built-in rules are seeded at startup; a rule you edit or disable is never overwritten, and a deleted one is restored. Unmatched shortfalls are `Unknown`, and each outcome records the rule that classified it. A Judge's own FAIL or NEEDS_REVISION is not counted as the Judge's shortfall.
- **Correctable.** `StageOutcomeService` can classify an outcome by hand (kept through later re-application) and re-apply the rules to past outcomes. There is no REST, MCP or dashboard surface yet; that follows in the rest of Phase 1. Phase 1, steps 4 and 5 of [MODEL_HETEROGENEITY.md](docs/MODEL_HETEROGENEITY.md).

### Stage outcomes record the runtime version, the model digest and the escalation record

- **Runtime version.** Each stage outcome now records the agent runtime's version: the first line of `<cli> --version` (`claude`, `codex`, `gemini`, `cursor-agent`, `mux`, `opencode`) run on the host that ran the attempt (the Admiral's host or the attempt's Harbor), or for an API-endpoint captain on an Ollama endpoint, `Ollama <version>` from `GET /api/version`. Values are cached per captain and Harbor for 30 minutes (a probe that answers nothing for 5 minutes). Exit handling waits at most 3 seconds for a value that is not cached; a probe that fails, times out or is still running leaves the value null and never fails the exit.
- **Model digest.** For an Ollama endpoint, the outcome records the model's digest from `GET /api/tags` (a model name without a tag matches `:latest`), with the endpoint's credential, cached per endpoint, Harbor and model. Other providers, unknown models, error responses and a loopback endpoint used by a Harbor attempt (which the Admiral cannot reach on the Harbor's behalf) leave it null.
- **Escalation record.** An escalation is now recorded as `Escalated`, with the new captain, even when the mission is still `Pending` for that captain (before, such an exit could be recorded as `Relaunched`), and the outcome records the commit the attempt left on the branch (`CommitHash`). When the mission later completes, each escalated outcome is linked to the attempt that finished it (`FinishedByOutcomeId`, `FinishedByCaptainId`), and `PriorWorkKept` says whether the finishing captain kept the escalated work (its commit is an ancestor of the finished commit) or replaced it; null when either commit or the repository is unavailable. Migration 93 adds the four columns on all four databases.
- **Purge removes outcomes.** Deleting or purging a mission (every `IMissionMethods.DeleteAsync` overload on all four databases, which every REST, MCP and WebSocket delete and purge path uses) and the SQLite retention sweep now delete the mission's stage outcomes. Phase 1, step 4 of [MODEL_HETEROGENEITY.md](docs/MODEL_HETEROGENEITY.md).

### Stage outcomes and failure-cause rules over REST, MCP and the clients

- **Read and correct suspected causes.** `GET /api/v1/stage-outcomes` (paged; filters by tenant for global admins, mission, voyage, vessel, captain, persona, model, cause, cause source, disposition, evaluation and end time), `GET /api/v1/stage-outcomes/{id}`, and `PUT /api/v1/stage-outcomes/{id}/cause` to classify an outcome by hand (recording who did it) or, with a null cause, hand it back to the rules. ### Cancelling a mission stops its agent

- **Cancel stops the agent before the mission is marked cancelled.** Cancelling a mission or a voyage on any surface (REST `DELETE /api/v1/missions/{id}` and `DELETE /api/v1/voyages/{id}`, MCP `cancel_mission` and `cancel_voyage`, WebSocket `cancel_mission` and `cancel_voyage`), and deleting a vessel with active missions, now goes through one shared cancel: the captain's process is stopped through the lifecycle that owns it (on its Harbor when it runs there) and the exit confirmed, then the captain is released, then the mission is set to `Cancelled`. Before, every path only changed the status and forgot the process, so an agent could keep running, and committing, on a Harbor after its mission was cancelled. REST mission cancel also never released the captain. When the stop is not confirmed, the cancel is refused (REST `409`, MCP and WebSocket `Conflict`) and nothing changes; voyage cancel lists such missions in `NotCancelled`.
- **Find and stop a Harbor job directly.** `GET /api/v1/harbors/{id}/jobs` (paged; `open=true` for jobs that have not ended) and `POST /api/v1/harbors/{id}/jobs/{jobId}/stop`, with the MCP tools `list_harbor_jobs` and `stop_harbor_job`, stop an agent no mission or captain still points at.

### Persona priorities: choosing a runtime adds it

- **No more unsaved priority choices.** The persona priority editor on the dashboard and mobile had a "Runtime for new priority" picker and a separate **Add priority** button; choosing a runtime without pressing the button and then saving stored an empty priority list without a word (this is how the Worker persona lost its Claude priority). The picker is now **Add priority** itself: choosing a runtime or API endpoint adds it to the bottom of the list at once. The TUI already added priorities through its own dialog.

### Stage-check time limit is a setting

- **`StageCheckTimeoutMinutes`** (default 15, 1 to 240) replaces the fixed 15-minute limit on each stage-check command (a vessel's build and unit-test commands, run in the dock after an API-endpoint or Mux stage). A vessel whose test command takes longer, such as a whole-solution `dotnet test`, always timed out and sent the captain back to "investigate". It is editable in `settings.json`, `PUT /api/v1/settings`, the dashboard and Harbor app server settings, the TUI, mobile, and `armada config set stageCheckTimeoutMinutes`. The timeout note now names the limit and how to raise it or narrow the check. A value outside the range answers `400` and changes nothing.

### One agent per dock after a long stage check

- **A stage check longer than five minutes no longer launches a second agent.** While a mission's exit handler ran its stage check, the health check's record that the exit was being handled expired after five minutes; it then probed the Harbor job's handle as a local process, read it as vanished, and resumed the mission as "interrupted by a server/Harbor restart". When the stage check finished it resumed the mission too, so two agents worked in the same dock and broke each other's builds. The health check now skips a process whose exit handler is still running, for as long as it runs; only one resume in place runs per mission at a time; and a resume that finds a newer agent already attached stands down.
- The interruption note no longer claims a server or Harbor restart when it cannot know one happened.

### Harbor stays responsive under load

A busy Harbor (several captains plus an open Vessels list) showed the macOS spinning beach ball. Two things fed it:
the activity log redrew its whole 500-line box once per log entry, and the Vessels list asked every vessel's Harbor
for sync status and branch counts on every 15-second refresh, about 45 git processes a second for 65 vessels. While a
process starts, .NET on macOS holds the allocator lock that the UI thread's text layout also needs.

- **Harbor: the activity log is redrawn in batches.** Entries from any thread are queued and added to the log at most
  four times a second, in one redraw, and not at all while the window is hidden or minimized (it catches up when it
  shows). Copy copies the full current view.
- **Admiral: git status is reused.** `GET /api/v1/vessels/{id}/git-status` (git fetch plus two `rev-list` commands)
  reuses a result for up to two minutes, or 15 seconds when it is an error, and requests that arrive while a read
  runs share it.
- **Admiral: branch divergence only for the page.** `POST /api/v1/vessels/{id}/branches/enumerate` lists branches
  with one `git for-each-ref` and measures ahead/behind (one `git rev-list` each) only for the branches on the page
  returned. `IGitService` gains `ListBranchTipsAsync` and `MeasureBranchDivergenceAsync`; `ListBranchesAsync` is
  unchanged.
- **Dashboard and mobile Vessels lists read only the rows on screen.** Sync status and branch counts are read for the
  visible rows, four at a time, and a vessel is read again only after two minutes (Refresh, or closing its branches
  dialog, reads it now). Branch counts use the new `getVesselBranchCount` (a one-branch page of the paged route)

  rows through a new `ListPane` `onVisibleItemsChange`.
- **TUI and .NET client.** The TUI Vessels screen reads statuses four at a time with the same two-minute reuse, using
  the new `ArmadaClient.GetVesselBranchCountAsync`. `ArmadaClient.MarkAskThreadUnreadAsync` is added, matching the

## v1.1.0 (2026-10-15)

### Delivery and handoff hardening for mixed runtimes

Mixed fleets (Claude Code, Codex, Mux, API endpoints, local and cloud models) now fail narrowly and recover by themselves instead of cascading. The audit and its status are in `archive/HANDOFF_EXAMINATION_RESULTS.md`.

- **Assignment is claim-first.** A mission is assigned only after its captain is claimed; a provisioning or launch exception rolls back the claim instead of releasing a captain that another mission now holds. A mission can no longer run twice, and a captain is no longer left Working with no process. Captain lifecycle writes (release, dock, process) are compare-and-swap.
- **One failing mission no longer stops the health loop.** Each phase (dispatch, merge queue, recovery, watchdogs) runs and fails on its own.
- **Failures are classified by kind, not by runtime.** Stream errors, inference errors, timeouts, 408 and 529/overloaded are transient rather than crashes. When a run reports several errors, the most significant one is kept. A Mux exit 0 with a failed or missing `run_completed` counts as a failure.
- **Output repair turn.** A Judge or Architect whose output breaks its contract (no verdict, conflicting verdicts, a missing lens or affected case, an invalid plan block) runs once more with the exact errors quoted before the mission fails (`MaxOutputRepairAttempts`, default 1, 0 to 3). Numbered narration is no longer turned into a Worker-to-Judge chain.
- **New Judge verdict `SPEC_CONFLICT`.** It reports a criterion that cannot be satisfied as written, with a `## Spec Conflict` section, so a person decides instead of rework repeating until the budget is spent.
- **Every runtime's stage is checked before handoff.** The workflow-profile build and test commands now run after Claude Code and Codex work stages too, not only Mux and API (`VerifyAllStageRuntimes`, default true). A check that also fails on the stage's base commit is not blamed on the captain. Build output from the check is reverted rather than committed.
- **Handoff keeps the branch.** Every stage records its exact commit, and the next stage starts from it even when the two stages run on different hosts. Leftover changes are not committed over a captain's own commit.
- **Captains that keep failing are taken out of rotation.** A launch failure backs off per captain and excludes it from the retry. A deterministic configuration failure quarantines the captain. A failed captain moves straight to Stalled or Quarantined, without an Idle gap in which it could be picked again.
- **Endpoint load and outages.** A transient resume waits with jittered exponential backoff (`TransientResumeDelaySeconds`, default 5, up to 60 seconds). `AgentSettings.MaxConcurrent` is enforced, and an endpoint can cap missions per base URL (`inferenceOptions.maxConcurrentMissions`). After three consecutive endpoint-level failures across captains, missions stop going to that base URL for two minutes; a clean run reopens it. API captains retry a failed inference call in the loop instead of ending the run.
- **Ollama context window.** `inferenceOptions.contextLength` is sent as `num_ctx` on Ollama and Ollama Cloud endpoints. An API captain whose prompt reaches 95% of the window stops with `context_limit_exceeded` instead of continuing on silently truncated history. Endpoints that set it run only on Harbors that advertise `api-inference-context-v1`; otherwise they run on the Admiral. Both settings are in the dashboard and TUI endpoint forms. The TUI form no longer drops `maxConcurrentMissions` when an endpoint is edited.
- **Streaming and first-response deadline for API captains.** `inferenceOptions.streaming` streams model responses, so the request timeout becomes an idle deadline (no data for that long) and long generations survive an idle-based proxy. `inferenceOptions.firstResponseTimeoutMs` gives a cold model load or a long prompt evaluation its own deadline. A stalled call fails as a transient `llm_timeout` whose reason names the phase, and partial tool calls from an unfinished stream never run. Endpoints that set either run only on Harbors that advertise `api-inference-streaming-v1`. Both are in the dashboard and TUI endpoint forms. A 502 or 504 that arrives only after a long wait (10 s or more) now says a proxy is cutting the request before the model replies, and what to change, instead of reporting a bare status. The .NET client no longer drops a nondefault `contextLength` or `maxConcurrentMissions` set through the options getter.
- **Gemini, Cursor and OpenCode failures are classified.** These text-mode CLIs had no provider-error parsing, so every non-zero exit was a crash. Their stderr is now read for explicit signals only: an HTTP error status written as a status, a Google RPC status (`RESOURCE_EXHAUSTED`, `UNAUTHENTICATED`, `PERMISSION_DENIED`, `UNAVAILABLE`, `DEADLINE_EXCEEDED`) or a network error code. A rate limit, an auth failure or an outage then gets the same handling as on Claude Code and Codex. Stdout narration is never parsed. The same applies on a Harbor.
- **A persona's default captain is a preference again, not a pin.** It used to be written onto each mission together with its tier, so a busy Premium default left a Premium floor that kept the mission Pending while Standard captains sat idle. The default is now consulted on every dispatch tick and never stored on the mission. Operator overrides and escalation targets keep their behavior.
- **The final integration slice integrates landed, finished work, and stops when a slice fails.** It used to start once every sibling was WorkProduced, Failed or Cancelled: before a sibling's work had finished landing, without a failed slice's work, and, with parallel slices and no automatic landing, without any sibling commits on its branch. It now waits while a sibling's merge-queue entry or completion is unsettled, then starts with the other slices' commits merged into its branch; a conflicting merge is aborted and left to the integration Worker with its files named, and a commit the dock cannot reach refuses the stage with the reason. A failed or landing-failed slice cancels the integration as `DependencyFailed`, and restarting that mission restores it. A slice an operator cancelled is left out and named as dropped. Manual landing and landing mode `None` cannot hold it forever. See docs/PIPELINES.md.
- **An integration slice lists only real slices.** Its merge list no longer names the Product Manager's (or Architect's) commit, which is the base every slice starts from.
- **Maintenance.** `MissionService` is split into partial-class files by concern with no behavior change, and the test harness rejects an unknown `ARMADA_TEST_DB_TYPE` instead of running on SQLite; the database suites were run against PostgreSQL 16, MySQL 8.4 and SQL Server 2022.
- **Mobile:** the app shows the Blocked status, has the Block Stages After a Failure switch in Server > Agent Settings, and its endpoint form carries streaming, first-response timeout, context window and the concurrency cap, so editing an endpoint on a phone no longer resets them.
- **Dispatch no longer reads each vessel's whole mission history per pending mission.** The vessel lock, broad-scope and shared-branch checks only need the vessel's Assigned and InProgress missions, but every pending mission loaded the vessel's complete history (with stored outputs and diffs) on every dispatch pass. They now read only the active missions.
- **Harbor jobs never share a process id with local work.** The Admiral keyed running work by one integer across its own processes, API captains' in-process ids and Harbor jobs, and a Harbor job kept the Harbor's own process id, which can equal a process on the Admiral (a Linux container and a Mac number their processes the same way, and both sides number API captains from 2,000,000,000). A Harbor job now gets an Admiral handle from its own range (from 1,000,000,000), restored jobs keep theirs, and API in-process ids start at a different point on each Admiral run.
- **A cancelled mission stays cancelled.** A completion can run for minutes (its stage check alone up to 15) after reading the mission; if an operator cancelled the mission meanwhile, the completion's later full write put it back to WorkProduced and the pipeline carried on. Every plain mission update now refuses to move a Cancelled mission anywhere but Pending (a restart), on all four databases, and the late writer sees Cancelled. Armada's internal status transitions are now documented in docs/PIPELINES.md.
- **Stopping a stage's captain no longer strands the stages after it.** Found live: a Worker failed by stopping its captain left its Judge Pending forever ("waiting for the Failed Worker to finish") and the voyage open, because that path did not cascade. A health-check phase now settles the waiting stages of any mission that ended Failed, LandingFailed or Cancelled without settling them: cancelled by default, Blocked with `BlockDependentsOfFailedStages` on.
- **A rework chain is written in one transaction.** A Judge's (or verifier's) rework creates several missions and re-points the stages after the reviewer; these were separate writes, so an interruption part-way could leave the later stages waiting on the rejected review, where recovery could pass them on. They are now written together (`CreateChainAsync` on all four databases) or not at all.
- **Verifier stages can block on a product defect.** A Test Engineer, Linter, or Usability Engineer that finds a defect its role may not fix used to report COMPLETE with the defect in its prose, so the work went on through the chain until the Judge found the same thing. It now ends with `[ARMADA:STAGE-OUTCOME] BLOCKED` and an `## Affected Case`, and the work goes straight back to the Worker, with a new verifier checking the rework and the Judge waiting for it. A block without a concrete affected case gets an output repair turn. API captains accept the blocked line as a finished reply.
- **Blocked status for stages held by a failed stage (opt-in).** With `BlockDependentsOfFailedStages` on, the stages waiting on a stage that failed, and a final integration slice whose sibling failed, show the new mission status `Blocked` (naming the failed mission) instead of being cancelled. The voyage stays open; restarting the failed stage returns them to Pending, and cancelling the voyage cancels them. Off by default, which keeps today's behavior. The dashboard and TUI show and filter the new status.
- **A killed Harbor no longer leaves an agent editing a dock behind it.** Found live by killing the Harbor mid-mission: the Mux captain it had started kept running, and the Admiral relaunched the mission into the same dock, so two agents edited one worktree. Harbor now records the agent processes it starts (`running-agents.json` in its settings folder) and, on its next start, stops any that are still running before it connects; a process that merely reused a recorded id is left alone. Update Harbor to get this.
- **Harbor missions ride out an Admiral restart.** Found live by restarting the Admiral mid-voyage: a Harbor mission that finished just before the restart had its completion replayed before its Harbor reconnected, so the stage check could not reach the Harbor, the captain was sent back to "fix" it, and the relaunch, refused while the Harbor was away, waited 10 minutes for the stall check. Now a recorded exit is replayed once its Harbor is back (up to 10 minutes), a stage check waits up to 3 minutes for a briefly disconnected Harbor, and a relaunch refused because its Harbor was offline runs on the first health check after that Harbor reconnects.
- **Rework state is stored, not read from titles.** A rework Worker's round and whether it was the escalated attempt are now mission fields (`ReworkRound`, `ReworkEscalated`; migration 91 on all four databases), so renaming a mission no longer resets its rework budget or hides an escalation. Missions stored before this are still recognized by their titles.
- **Gemini, Cursor and OpenCode hand off their reply, not their transcript.** These CLIs run in plain-text mode, where stdout is the agent's reply and stderr its progress. On a clean exit the reply is now written as the launch's final-message file (as Claude Code, Codex and Mux already do), so the next stage, the Judge verdict and the Architect plan are read from the reply. A file the CLI wrote itself is kept, and a failed run writes none.
- **An Architect fan-out interrupted by an Admiral restart is finished on recovery.** Recovery used to skip Architects, so a restart after the plan was produced but before every slice was written left the voyage waiting forever, or running with slices (possibly the integration slice) silently missing. The fan-out now marks the Architect complete only after its last write, and recovery reconciles an unmarked Architect in a running voyage against its own plan: it runs a fan-out that never started, creates a missing slice or stage chain once, and applies the plan's dependencies only to slices that have not started.
- **API captains compact their history instead of running out of context.** With `inferenceOptions.contextLength` set, a conversation that reaches 80% of the window (by the provider's count or a local estimate, since Ollama does not count cached prompt tokens) has its oldest large tool outputs replaced by one-line notes; the six most recent outputs, the mission brief and every assistant turn stay whole, and the captain can rerun a tool it still needs. A prompt that reaches the 95% tripwire while still below the window is compacted and the run continues; it stops with `context_limit_exceeded` only when there is nothing left to compact. Logged as `[context]` lines. Update Harbor too.
- **Slow open models are no longer mistaken for stalled captains.** Stall detection watches captain output, and an API captain wrote a line only between model turns, so one long generation on a slow model (more than the 10-minute stall threshold) looked like a hung captain. A model call still in flight now writes a progress line every minute (`[inference] waiting for the model`); the call stays bounded by its own request, first-response and idle deadlines. Update Harbor too: Harbor-hosted API captains run this code there.
- **Validating a local model address says what it could not check.** Validation runs on the Admiral host, so for `localhost` or a loopback address the result now carries a note: an API captain whose missions run on a Harbor calls that address on the Harbor's computer, which the check never reached. Shown in the dashboard and TUI validation results (`note` in the API).
- **TUI:** Server Settings > CLI Tool Permissions gains "Default answer on timeout" (Deny or Approve), matching the dashboard.
- **Tier routing reads model sizes and vendor defaults.** A model with 8B parameters or fewer (`qwen2.5-coder:7b`, `llama3.2:3b`) now counts as Economy, so explicitly tiered Standard or Premium work no longer goes to it. A Claude Code, Codex or Gemini captain with no model set runs its vendor's default flagship model, so it can now take Premium work instead of leaving Premium missions Pending; it still ranks as Standard, so untiered and Standard routing order is unchanged. Nothing needs configuring: an explicit captain `tier` is still taken as declared, and an unknown model is still Standard.
- **Unhealthy endpoints are skipped at dispatch.** A captain whose model endpoint failed a health check in the last 15 minutes is not picked for new work; an older result does not block.
- **A Worker that stops mid-task is re-dispatched, not handed off.** Found live: a local model ended its run after three minutes while still reading files, with no commit and no completion line, and Armada recorded it as finished work. A Worker that ends on the commit it started from, with no diff and no `[ARMADA:RESULT] COMPLETE` line, now goes through the bounded no-op re-dispatch; once that is spent it fails with a reason that points at context and output limits.
- **Strict captain assignments are never escalated to another captain.** Found live: a strictly assigned Mux Worker that kept hitting endpoint errors was finished by a different model. It now fails instead, so a test's model identity holds.
- **Missions that continue one branch take turns.** Two slices that both build on an earlier slice were handed the same branch, so the second launch failed when git refused a second worktree. A mission now waits while another active mission holds its branch (assignment blocker `BranchInUse`, naming the holder), then stacks on it.
- **Endpoint outages are ridden out.** Found live: a proxy restart failed a Mux Worker 38 seconds into the outage, after its three resumes, losing eight minutes of work in progress. Transient model and endpoint failures now keep resuming in place with the capped backoff for `TransientOutageGraceMinutes` (default 10, 0 to turn off) before the mission fails, and the repeated failure is noted once in the mission instead of once per resume. A mission that still fails from a transient cause is classified `Infra`, not `Crash`, so it goes to a person instead of an automatic rescue against the same endpoint.
- **Stopping an API captain waits for its loop.** `StopAsync` now returns only once the run has left its current model call or tool (up to 15 seconds), so a relaunch into the same dock never overlaps a loop that is still editing files.
- **Rework that does not reach the reported defect switches captain early.** When a Judge rejects a rework round with the same concrete affected case as the previous round (the same file, ignoring line moves, or the same scenario), the rework is treated as stagnant and escalates now, the same way an unchanged commit already did, instead of spending another full round.
- **Harbor runs headless when its UI cannot start.** Found live: restarting the Mac Harbor while the display slept failed in Avalonia's render timer (-6661), and the computer stayed offline until someone woke it. Harbor now falls back to running its link without a window (logged as `running headless`), and `--headless` starts that mode on purpose. The link loop moved out of the main window into `HarborLinkHost`, which both modes share.
- **Harbor capacity waits.** When every capable Harbor is at capacity, the mission waits for a slot instead of starting on the Admiral, where the runtime may be missing. A mission whose dock cannot be placed now says so in its assignment blocker (`PlacementWaiting`, with the reason) instead of reporting that it will be assigned on the next cycle. The no-eligible-Harbor reason names the capability that is actually missing. Dock affinity no longer pins a launch to a Harbor that cannot run the captain's runtime.
- **Harbor link.** A job message is acknowledged only after the Admiral has handled it. Large frames are decoded once. The vanished-job grace period restarts on reconnect. Requests on a replaced link fail at once. Job stops run off the receive loop.
- **Runtime lifecycle.** Stop sends SIGTERM before killing; the exit handler no longer blocks thread-pool threads. Captain heartbeat writes are throttled, and Mux output buffers are bounded.
- **Pipelines settle correctly.** Halting a voyage of independent missions stops their running processes, not just their records. A completion still in flight no longer lets a voyage settle early. Restart recovery keeps the Judge gate, and crash rescue opens only for standalone work. No-op re-dispatches have their own counter (migration 89), separate from resumes and interruptions. The no-op and missing-dock paths release the captain and settle the voyage.
- **Autonomous recovery stays bounded.** A rescue mission is flagged as one (`missions.is_rescue`, migration 90) and is never rescued itself, even after its original mission and incident are purged. Before this, purging the original orphaned its failed rescues, and each one opened a new rescue chain. A landing refused by a dirty checkout or by unpushed commits on the target branch is recorded as `Infra`, an environment problem a rescue cannot fix, so it is left for a person; the reason says to commit or stash and retry landing.
- **Claude Code final message.** Claude Code missions now write the final assistant message as the handoff artifact, as Codex, Mux and API captains already did, instead of handing off a trimmed transcript.
- Update Harbor alongside the Admiral: the Harbor-side link, stop and context-window changes apply only to an updated Harbor.

### Frontier models plan and review, local models do the work
Armada can now run one job across Claude Code, Codex, and a local model through mux (for example GPT-OSS 20b on your own GPU) on one Harbor, with planning and review on the frontier captains and the implementation on the local one, and land the result on GitHub without anyone stepping in.

Finished work lands with the server's landing mode, MergeAndPush by default, as soon as the last stage completes. The Judge is still the automatic gate: a Judge that does not PASS stops the pipeline. Existing installations keep their pipelines as they are.
- **Routing.** A mission dispatched without a persona (a plain dispatch, `create_mission`, a fleet action) is routed as a Worker, so the Worker persona's captain priorities apply; before, it went to whichever idle captain sorted first by name. MCP `dispatch` applies per-step captain assignments before the first stage is assigned (it used to save them afterwards), and accepts `landingMode` and per-mission `requestedCaptainId`, `tier`, and `persona`. Reasoning effort was dropped for every runtime on a Harbor. Both now travel with the launch.
- **Work a model forgot to commit is kept.** When a captain finishes with uncommitted edits, Armada commits them before taking the diff. Before, the diff was empty, the mission showed Complete, and the edits were deleted with the dock.
- **mux runs are read correctly.** A run that completes after a denied or invented tool call (mux exits 1 or 2 with `completed_with_errors`) is a success, and its final reply is rebuilt from the stream when mux did not write it. Real failures say why: "mux stopped: reached the 50-iteration limit (max_iterations_reached)". Iteration, budget, repetition, and context-window stops fail the mission without counting toward the captain's crash-loop quarantine. Live activity, `[ARMADA:...]` markers, and readable log lines now work for mux, and Codex and Mux provider errors are classified on Harbor runs.
- **Token usage is real.** Usage is read from the runtime's raw output as it streams, so mux (contract 2), Claude Code, and Codex missions record reported tokens instead of estimates, and mux records carry the endpoint's model (for example gpt-oss:20b) instead of "Mux".
- **Project rules reach every runtime.** A runtime whose instructions file is not the repository's own (MUX.md, CODEX.md, GEMINI.md, CURSOR.md) now gets the repository's AGENTS.md, else CLAUDE.md, merged in; mux used to load only Armada's MUX.md and skip the project's rules.
- **Review gates over MCP.** New `approve_mission_review` and `deny_mission_review` tools (a person's credential is required; captain sessions are refused). `transition_mission_status` no longer moves a mission out of Review, which skipped the stage handoff.
- **Pipelines recover.** A gated Judge that does not PASS goes to Review with its reason instead of failing the voyage, so a person can override it. Approving an Architect whose plan cannot be parsed cancels the following stages instead of leaving them Pending forever. The Architect's plan is read only from its own output or committed plan, never from its description (which holds the user's request), and each Worker it creates gets the overall objective and the plan outline. Restart (MCP, REST, WebSocket, one implementation) keeps a later stage's branch, reopens the voyage, and restores the stages cancelled because of the failure; REST restart of a mission in the wrong state now returns 409. A crash in one pipeline stage cancels only that chain; sibling chains and missions in Review are kept.
- **Local-model work is checked before it moves on.** When a Mux (or API endpoint) captain finishes a work stage (Worker, Usability Engineer, Test Engineer, Linter), Armada runs the vessel's workflow-profile build and unit-test commands in the dock. If they fail, the captain is resumed with the compiler or test output; frontier captains are trusted and not checked. Found when gpt-oss reported a Timestamps change as done with a missing brace.
- **A local Worker that cannot finish is escalated.** When a Mux stage keeps failing after its resumes (model endpoint errors, iteration limits, a failing stage check), its work is committed on the branch and one last attempt goes to the captain that planned the voyage (its Architect, else Product Manager), instead of failing the voyage. The resume note now also tells the model that every line in its own `git diff` is its to fix, and to write files without the line numbers `read_file` shows.
- **Finished voyages look finished.** When a voyage completes, its intermediate pipeline stages (the ones a later stage built on) are marked Complete instead of staying WorkProduced. A WorkProduced result nothing builds on (landing mode None) keeps its status.
- **A Judge's revision request is acted on.** When the Judge (for example on Codex) asks for concrete changes, the work goes back to a Worker on the same branch (for example on mux) with the review as its instructions, and a new Judge checks the result; up to two rounds; then one escalated round goes to the captain that planned the voyage (for example Claude Code), and only after that does the chain fail. Found when a Codex Judge rejected a gpt-oss change for a stray file and leaky tests, which used to end the chain with nothing landed.
- **Local-model hiccups do not end a mission.** When the model endpoint fails in a way that clears on the next request (an HTTP 5xx, for example Ollama answering "error parsing tool call" when gpt-oss emits a malformed tool call; a dropped connection; a timeout), or a mux run stops at its iteration or token budget, the captain is relaunched in the same dock with its edits intact and a note telling it to check `git status` and continue, up to `maxRecoveryAttempts` (default 3) times. Only then does the mission fail.
- **Interruptions are retried more.** A mission interrupted by an Admiral redeploy or a Harbor that dropped (exit -1) is re-dispatched at least 3 times (more when `maxNoOpRedispatchAttempts` is higher) before an interruption fails it; it used to be once, so two redeploys during one long mission failed it.
- **Two Harbors on one computer.** `ARMADA_HARBOR_HOME` points a Harbor at its own settings, docks, and logs folder, for example to run a test Harbor against a second Admiral without touching your main one. Require Harbor for launch is also in the TUI's Server settings.
- **No more silent retry loops.** A captain that cannot start (its CLI missing where the mission landed) backs off from 30 seconds to 5 minutes and the mission shows why (`LaunchFailing`); after six missing-CLI failures it fails with a reason. A captain marked Stalled by a provider condition returns to Idle after 15 minutes.
- **Harbor link survives blips.** Job output and exits produced while the link is down (Wi-Fi drop, closed lid, Admiral redeploy) are kept on the Harbor and replayed after the reconnect. A job the Harbor no longer has is reported within about 20 seconds and its mission redispatched, a job the Admiral no longer owns is stopped, and a silent link is closed after max(45 s, 3x the heartbeat interval).
- **Harbor finds your CLIs.** A Harbor started from Finder or a login item imports your login shell's PATH (plus ~/.local/bin, ~/.dotnet/tools, /opt/homebrew/bin, /usr/local/bin) and advertises a runtime only when its CLI is found; the window lists available and missing runtimes.
- **Landing is safe in your own checkout.** MergeAndPush and LocalMerge restore the branch your checkout was on, fetch and fast-forward the target first, and refuse before merging when your local target has unpushed commits. The merge-commit template is honored on fast-forwards. The PR reconciler only pulls when the checkout is on the target, clean, and behind.
- **Merge queue.** An entry whose Harbor is offline waits in the queue instead of failing; genuine failures also mark the mission LandingFailed. Deleting a Failed entry no longer deletes the only copy of its branch. Entries resolve their Harbor from the most recent dock on the branch, leftover integration worktrees are pruned, landed missions raise the usual events, an already-landed mission cannot be enqueued, and Needs You shows the mission title and the failure output.
- **Configuration fixes.** Personas with spaces in their names (Test Engineer, Usability Engineer, Product Manager) could not be read, edited, or deleted through REST or the dashboard; every name-valued route now decodes its parameter. Editing a captain from the Captains list kept wiping AllowedPersonas and PreferredPersona, and editing a persona from the Personas list cleared its default captain; updates now change only what they send. Require Harbor for launch is in Server settings and the settings API. The Mux captain form validates temperature and max tokens, drops the "ask" approval policy that mux print rejects, and names the Harbor it read endpoints from. Mission detail shows the Harbor that ran the mission and the captain's runtime. The Dispatch page says that choosing a captain for a step overrides the persona's priorities.

### Model endpoints: authentication types and extra headers

### Fixes
- A CLI permission prompt whose request cannot be shown to anyone who could decide it is now denied at once instead of blocking the captain until the prompt timeout (about 600 s). Before, when posting the Ask card failed (the thread was missing, or SQLite reported "database is locked" after its busy timeout), the error was swallowed and the request stayed Pending with no card. Now a transient database failure is retried once after a short backoff, and then the captain gets "Armada could not show this permission request in the conversation (reason); denied." (mission prompts whose request cannot be stored get the same answer, naming the approvers). The request is recorded as `Denied` with the new decision source `DeliveryFailed` and the reason, a warning is logged, and `cli_permission.resolved` is sent so the inbox and Approvals centers show nothing pending.
- Captains no longer stop to ask about low-stakes choices with a sensible default (for example which framework to run a multi-targeted .NET project with). The built-in `ask.system` prompt gains a "Making decisions" section and `mission.rules` says a mission cannot wait on answers: choose the default, say what was chosen, and ask only when a choice is risky, hard to undo, changes shared state, or the request is genuinely ambiguous. Untouched built-in templates are upgraded on startup; edited templates are left as they are (Prompt Templates > Reset to default picks up the new text).
- SQLite writes can no longer starve each other. One CLI permission insert waited 17 s on a Windows runner (the E2E CliPermissions flake) because Microsoft.Data.Sqlite retries a locked write by sleeping 150 ms and trying again, and most writers (request-history inserts on every REST call, entity creates, updates and deletes, data expiry, restore) wrote without the provider's in-process lock, so they kept winning while the queued insert lost every retry. Every write the process makes to a SQLite database now goes through one first-in, first-out write gate per database file (`SqliteWriteGate`, shared by all drivers and services on that file): a write is granted after the writes that asked before it and never after one that asked later. Request-history inserts are group-committed (one transaction and one turn at the gate per burst), request-history retention deletes run in chunks, and data expiry takes the gate per statement. Provider connections set `busy_timeout` and `synchronous=NORMAL` (the WAL-mode recommendation; commits no longer flush the WAL). Each committed write transaction is checked against the gate, and the test runners refuse any write that bypasses it.

### CLI tool permissions
- New policy for a CLI captain's own tools (shell commands, web fetches, file tools outside the accepted edits), `CliPermissionPolicyEnum`: `Refuse` (tools that need approval are refused; the turn or mission continues without them), `ApproveInArmada` (the CLI's permission prompts become CLI permission requests that an approver allows or denies in Armada), and `Bypass` (the runtime's own permission-bypass flag). Armada's own MCP tools are governed as before (Ask proposals and per-tool authorization).
- Resolution, most specific first (`CliPermissionPolicyResolver`). Ask turns: the thread's `CliPermissionPolicy`; the captain's `CliPermissionPolicy` (a captain-level `Bypass` only when `Ask.CaptainAutoApprove` is on); when `Ask.CaptainAutoApprove` is on, the captain's legacy `autoApprove` runtime option (absent or true is `Bypass`, false is `Refuse`); `Permissions.AskDefaultPolicy`. Missions: a vessel `AutoApprove` of true is `Bypass`; the captain's `CliPermissionPolicy`; the captain's explicit legacy `autoApprove` (true is `Bypass`, false is `Refuse`); `Permissions.MissionDefaultPolicy`. A vessel `AutoApprove` of false turns a mission's `Bypass` into `Refuse`. `ApproveInArmada` falls back to `Refuse` when the runtime has no permission prompt hook (`RuntimeUnsupported`; only Claude Code and ApiEndpoint have one), a Claude Code launch has no scoped MCP token (`NoSessionToken`), or the captain runs on a Harbor (`RemoteHarbor`). Each resolution carries `Requested`, `Effective`, `Source`, `FallbackReason`, and a one-line `Note` that says where to change it.
- Defaults: `Permissions.AskDefaultPolicy` is `ApproveInArmada`, so a shell command in an Ask turn waits for an approver instead of being silently refused (Ask turns can be started by any user of the tenant, so they never bypass by default). `Permissions.MissionDefaultPolicy` is `Bypass`, which is the previous behavior (captains ran with their bypass flag unless `autoApprove` was false): missions run unattended, and a prompting default would hold every mission on approvals. Milestone narrations and conversation summaries never prompt (nobody is waiting for them), so `ApproveInArmada` runs them as `Refuse`.
- Claude Code integration: an `ApproveInArmada` launch adds `--permission-prompt-tool mcp__armada__cli_permission_prompt` to `--permission-mode acceptEdits --allowedTools mcp__armada` and raises `MCP_TOOL_TIMEOUT` to the prompt timeout plus two minutes. The new `cli_permission_prompt` MCP tool (callable only by the captain's own mission- or thread-scoped session) applies rules, records the request, and holds the call until an approver decides, the request expires, or the session ends, then answers `{"behavior":"allow","updatedInput":{...}}` (the original input) or `{"behavior":"deny","message":"..."}`.
- Requests (`CliPermissionRequest`, `cpr_`): tool name, redacted input, a one-line summary (command, URL, or path), a suggested rule, captain, mission, voyage, vessel, or Ask thread, status (`Pending`, `Allowed`, `Denied`, `Expired`, `Cancelled`), decision source (`Approver`, `AllowRule`, `DenyRule`, `Timeout`, `Cancelled`), expiry, and the caller's `CanDecide` and `CanRemember`. Every prompt is recorded, including rule decisions. Pending requests are cancelled when the Ask turn ends or the mission's captain process exits; the periodic Ask tracker sweep resolves requests no call is waiting for (for example after a restart).
- Rules (`CliPermissionRule`, `cpl_`) use Claude Code permission rule syntax: `Bash`, `Bash(git status:*)` (prefix), `Bash(npm run *)` (glob), `Bash(exact command)`, `WebFetch(domain:example.com)`, `WebFetch(domain:*.example.com)`, `Read(...)` and `Edit(...)` with gitignore-style paths (`//abs/path/**`, `~/path`, or relative to the mission dock), `mcp__server`, `mcp__server__*`, and `mcp__server__tool`. Scope `Global` (the tenant; a global admin's rule without a tenant applies to every tenant), `Vessel`, or `Captain`. A matching deny rule denies without asking, otherwise a matching allow rule allows; deny wins. Bash command lines are split at `&&`, `||`, `;`, `|`, `|&`, `&`, and newlines outside quotes: every subcommand must match an allow rule, any subcommand matching a deny rule denies, and a command with substitution or unbalanced quotes is never allowed by a `Bash(...)` rule (it goes to an approver).
- Who may act (`CliPermissionAccess`, shared by REST, MCP, WebSocket, and the inbox): global admins, the tenant's tenant admins, and the owner see a request; global admins and the tenant's tenant admins decide it (`AllowOnce`, `Deny`), and the owner too only when `Permissions.AllowOwnerApproval` is on (default false); `AllowAndRemember` (also stores an allow rule, default scope `Captain`, pattern defaulting to the suggested rule) is for admins only. Captain sessions never decide, MCP decisions need a presented credential (not the unauthenticated loopback identity), and an Ask thread's captain cannot call the decide, rule, or policy tools (refused, never proposed). Rules are created, changed, and deleted by global admins or by tenant admins within their tenant. A captain's policy is set by global admins or tenant admins of its tenant; a thread's policy by the thread owner, and `Bypass` only when the owner is an admin.
- `Permissions.PromptTimeoutSeconds` (default 600, clamped to 10..3600): an undecided request becomes `Expired` and the captain is told no approver decided in time. All `Permissions` settings apply to the next launch.
- Ask transcript: a request raised in a thread posts a `CliPermission` card (tool, command or input, captain, expiry countdown, status; Allow once, Allow and remember, Deny when the viewer may decide, otherwise "Waiting for an admin to decide"), refreshed through `ask.message` when it is decided. Tool calls the CLI refused for lack of permission (Claude Code's typed `permission_denials` on the result event) are stored as `AskMessageToolCall.PermissionDenied` and render as `[x!]` with an explanation of the effective policy, its source, and where to change it. The conversation header has a CLI tools control (Inherit, Refuse, ApproveInArmada, Bypass for admins with a confirmation) and shows the effective policy, its source, and any fallback.
- Mission logs start with an Armada line holding the resolution note (policy, source, fallback, and where to change it), so a refused tool in the log has its explanation above it.
- Per runtime: Claude Code supports all three policies. Codex (`--sandbox workspace-write` versus its approval mode; `full-auto` stays sandboxed on macOS and Linux, only `dangerous` and Windows `full-auto` bypass), Gemini (`auto_edit` versus `yolo`), Cursor (without or with `--force`), OpenCode (without or with `--auto`), and Mux (`--approval-policy deny` versus `--yolo`; an explicit Mux approval policy on the captain wins) support `Refuse` and `Bypass`, and run `ApproveInArmada` as `Refuse`. Harbor launches apply `Refuse` and `Bypass` through the captain's auto-approve option and run `ApproveInArmada` as `Refuse`. ApiEndpoint captains apply the policy in-process to their built-in shell tool `run_process` (and to nothing else: their file read, write, edit, and delete tools are not governed): `Refuse` refuses it, `ApproveInArmada` turns each call into a CLI permission request without needing an MCP token, `Bypass` runs it. Direct captain chat and planning sessions keep their previous behavior.
- Inbox: new kind `cli_permission` (severity Warning) with `InboxItem.CliPermission` (the request) and `InboxItem.ExpiresUtc`; it links to the owner's own Ask thread or to `/cli-permissions?request=<id>`. WebSocket: `cli_permission.requested` and `cli_permission.resolved` (`requestId`, `status`, `request`) go to the request's approvers and owner, each copy with that recipient's `canDecide` and `canRemember`; `ask.tool` gains `permissionDenied`; new commands `list_cli_permission_requests` and `decide_cli_permission_request`.
- REST: `GET /api/v1/cli-permissions/requests`, `GET /api/v1/cli-permissions/requests/{id}`, `POST /api/v1/cli-permissions/requests/{id}/decide` (403 when the caller may not decide, 409 when no longer pending), `GET`/`POST /api/v1/cli-permissions/rules`, `GET`/`PUT`/`DELETE /api/v1/cli-permissions/rules/{id}`, `PUT /api/v1/captains/{id}/cli-permission-policy`, `PUT /api/v1/ask/threads/{id}/cli-permission-policy`, and the `Permissions` object on `GET`/`PUT /api/v1/settings`. New fields: `Captain.CliPermissionPolicy` (accepted on create, kept by captain updates), `AskThread.CliPermissionPolicy` and `AskThread.CliPermission`, `AskMessage.CliPermissionRequest`, `AskMessageToolCall.PermissionDenied`, and `AskThreadDetail.PendingCliPermissions`.
- MCP: `cli_permission_prompt`, `list_cli_permission_requests`, `get_cli_permission_request`, `decide_cli_permission_request`, `list_cli_permission_rules`, `create_cli_permission_rule`, `update_cli_permission_rule`, `delete_cli_permission_rule`, and `set_captain_cli_permission_policy`.
- Dashboard: a CLI Tool Permissions page (`/cli-permissions`: pending and past requests, rules), Settings > CLI Tool Permissions, the captain policy on captain pages, and the permission card and header control in Ask. TUI: CLI permission requests in Approvals (decide, remember with an editable rule) and the permission card in Ask (see below for the rest).
- Schema migration v78 on SQLite, PostgreSQL, MySQL, and SQL Server: `cli_permission_requests` and `cli_permission_rules` tables, `cli_permission_policy` on `captains` and `ask_threads`, and `permission_denied` on `ask_message_tool_calls`.
- Retention: `Retention.CliPermissionRequestRetentionDays` (default 90, 0 never, clamped to 0..3650) deletes allowed, denied, expired, and cancelled requests decided longer ago than that; pending requests are never deleted. Deleting an Ask thread (by the user or by `Retention.AskThreadDeleteAfterDays`) deletes its requests. The dashboard and TUI Data Retention sections show the new field.
- A prompt call the captain cancels (`notifications/cancelled`, which Claude Code sends when a tool call is interrupted) now resolves its request as `Cancelled` at once instead of holding it until the prompt timeout: the MCP adapter hands each tool call's cancellation token to the handler. A connection that drops without a cancel is resolved when the captain process exits or the Ask turn ends (as before), or by the timeout.
- `run_process` (the ApiEndpoint built-in shell tool) rules take Bash specifiers on the command line: `run_process(git status:*)`, `run_process(npm run *)`, or an exact command. A shell command line is split like Bash (every part must be allowed; substitution is never allowed); a call with an `args` vector is one command (the command followed by its arguments, no shell). The suggested rule, and so the default of Allow and remember, names the command (`run_process(git status:*)`, or the exact command when the program is not a plain word) instead of the bare tool, which allowed every shell command. The rule dialogs (TUI) warn when a pattern allows every shell command for its scope (`CliPermissionRuleMatcher.IsUnrestrictedShellRule`).
- TUI: the CLI Tool Permissions hub (`/cli-permissions`, sidebar SYSTEM, `g k`, palette) with Requests (status filter, decide with `a` / `A` / `d` or the header buttons, the inbox's `?request=` link) and Rules (scope filter; create with the dashboard's validation and vessel or captain pickers; edit pattern, action, and description; delete with confirmation; read-only for non-admins). Settings > Server has the CLI Tool Permissions section (read-only for non-global-admins; Bypass only after the strong warning). The captain form and page show the captain's policy (admins only; Bypass after the warning; saved through its own endpoint). The Ask header has a CLI tools line with the effective policy and any fallback (`p` or a click to change it). Ask CLI permission cards have clickable [Allow once], [Allow and remember], and [Deny] buttons; the pending strip above the composer counts permission requests too; `cli_permission.*` events update cards live; new requests toast (with Open), ring, and raise an OS notification unless the conversation is on screen. The mission page shows the policy note from the top of the mission log. A tool call the CLI refused is always `[x!]`, even when its ok flag was not false.
- TUI decisions from wherever the user highlights: `a` / `r` act on the pending decision the highlighted block belongs to (its card, the captain reply of the turn that proposed it, a CLI permission card, or a work card row whose mission waits on a permission request or a review), `A` and `d` allow-and-remember or deny a CLI permission request, a chooser opens when there are several, and on a block with nothing to decide a hint says so (and that Alt+Down jumps to the pending one) instead of the key doing nothing. ### Self-rebuild ("Rebuild Armada")
- Added a dashboard **Rebuild Armada** button (Server page) that rebuilds the Admiral from its own source and cuts over to the new build with near-zero downtime -- so changes landed by captains can be picked up without leaving the dashboard. Designed for the native single-box deployment where Armada's source is itself a vessel.
- A/B slot layout: each rebuild publishes into a fresh versioned slot (`~/.armada/bin/slots/<yyyy-MM-dd_HHmmss_sha>/`) from a detached `git worktree` at an operator-chosen ref while the running server keeps serving, then flips a `current` pointer file and hands over via the existing detached-child restart baton. Publishing to a new slot sidesteps the Windows file lock on the running executable, so the build runs with no downtime and only a successful publish triggers a cutover -- a failed build never disturbs the running server.
- The database is backed up before every cutover. Operator **rollback** reverts to the previous slot; when the rebuild migrated the schema it first restores the pre-rebuild backup (discarding data written since cutover), otherwise it relaunches the previous slot with no restore.
- REST API: `POST /api/v1/server/rebuild`, `GET /api/v1/server/rebuild/status` (live build log), and `POST /api/v1/server/rollback`. New settings: `SelfVesselId` (which vessel holds Armada's source), `RebuildSlotRetentionCount`, and `RebuildSupervisorHarborId`.
- Optional Harbor-supervised cutover: when `RebuildSupervisorHarborId` names a connected on-box Harbor, the Admiral arms it with a one-shot `deferredLaunch` instruction before exiting; the Harbor launches the new slot, health-checks it, and rolls back to the previous slot if it does not come up. Otherwise the in-process baton is used (no automatic rollback). Two new Harbor protocol messages (`deferredLaunch`/`deferredLaunchAck`) documented in `docs/HARBOR_PROTOCOL.md`.
- Dashboard: a build-ref branch picker (from the source vessel's branches) plus a free-text tag/commit box, a live build-log viewer, a Roll Back action, and a Rebuild settings card to designate the self vessel and slot retention.
- Local-clone self vessels are buildable: `add_vessel` records a vessel's `WorkingDirectory` when its `repoUrl` is a local clone (a `file://` URL or an existing local git path), so a vessel pointing at an on-disk checkout can be designated `SelfVesselId` and built from its working tree. The Server page's branch picker also resolves branches from `WorkingDirectory`, so it now populates for such vessels instead of showing only a confirm dialog.
- Cross-platform cutover fix: the replacement-process launcher now uses `UseShellExecute=false` on every platform (Windows, Linux, macOS). It previously used shell-execute on Windows, which is incompatible with passing the predecessor-PID handoff environment variable and made the in-process cutover fail with "the replacement process could not be launched"; a `UseShellExecute=false` child still outlives the parent on all three platforms.
- Pre-rebuild database backups are pruned after each rebuild to the newest `RebuildSlotRetentionCount` (the most recent remains as the rollback safety net) so they no longer accumulate without bound.
- On Windows the dashboard build step during a rebuild runs through `cmd.exe` so `npm` resolves from PATH the same way an interactive shell does.
- Full design, task tracking, and safety rails documented in `docs/SERVER_REBUILD.md`. Self-rebuild is experimental in 1.0: it targets the native single-box deployment and is unit-tested (slot management and the deferred-launch protocol); the Harbor-supervised cutover path has not been verified end to end.

### Security
- **Breaking:** every REST route and MCP tool declares an explicit authorization requirement in a central registry, checked before the handler runs; undeclared routes and tools fail closed, and a test fails when one is missing. 19 enumerate routes now need only authentication; check-run writes and Harbor probes need a tenant admin.
- **Breaking:** MCP is authenticated by default; unauthenticated calls are accepted only on a localhost-bound listener from localhost (`Mcp.AllowUnauthenticatedLoopback`, default true); `backup`, `restore`, and `stop_server` require an admin credential.
- **Breaking:** `POST /api/v1/server/stop`, `restart`, `rebuild`, and `rollback` always require an admin (`RequireAuthForShutdown` is deprecated and ignored). Previously they needed no login by default, and rebuild could run a build from a caller-chosen path.
- The dashboard prompts for a new password at the first sign-in as `admin@armada` with the default password (`PUT /api/v1/account/password`; Skip for now keeps it after a risk confirmation), and changing it disables the `default` bearer token; administrators see a warning while defaults are in use; the Admiral refuses non-localhost hostnames with default credentials unless `AllowDefaultCredentialsOnNetwork` is set; new `ARMADA_INITIAL_ADMIN_PASSWORD` for headless and Docker installs.
- `AllowSelfRegistration` now defaults to false; the system API-key identity can no longer log in with a password; tenant admins can no longer modify or mint credentials for global admins; Harbor links must present a valid credential unless both ends are on localhost.
- New per-captain `autoApprove` switch runs CLI captains without their auto-approve flags; `audit.command` events are recorded for workspace exec, fleet action commands, check runs, Harbor probes, and merge-queue tests (only global admins can delete audit events).
- Bearer tokens are shown once at creation and masked on reads; remote-tunnel secrets are masked in settings; request history redacts secret-bearing keys, secret-shaped values, and query strings; deleting a vessel only removes directories inside the managed repos and docks directories.
- Containers run as non-root on pinned base images (the dashboard container listens on 8080); new `security.yml` workflow scans NuGet and npm dependencies; new `docs/SECURITY_REVIEW.md` and `SECURITY.md`.
- Removed: the keyword `POST /api/v1/ask` responder and the `armada ask` CLI command (use Ask Armada threads).
- Fixed: the MCP listener now binds when the hostname is `0.0.0.0`.
- **Security (tenant isolation):** MCP `enumerate` no longer returns other tenants' records. The mission summary path (the default) and `model_endpoints`, `harbors`, `releases`, `check_runs`, `personas`, `prompt_templates`, `pipelines`, `playbooks`, `jobs`, `workflow_profiles`, `project_profiles` and `skills` now use the caller scope of their REST lists. - Mission-scoped MCP tokens (`Mcp.MissionScopedTokens`, default true): every mission launch mints a token bound to the mission, its owner and its captain (MCP only; refused on REST, `/ws` and the Harbor link; stops working once the mission leaves Assigned / InProgress) and binds the captain's Armada MCP connection to it, so mission captains act as the mission's owner instead of the unauthenticated loopback identity. A mission-scoped caller may update the context of its own mission's vessel.
- New tenants no longer get `admin@armada` / `password`: `POST /api/v1/tenants` takes an optional `AdminPassword` or generates a random one returned once (`TenantCreateResult.AdminEmail` / `AdminPassword`). A user changing their own password through `PUT /api/v1/users/{id}` must send `CurrentPassword` (400 missing, 403 wrong).
- Dashboard and TUI follow the new contracts: editing your own user with a new password asks for and sends `CurrentPassword` (a 403 reads "Current password is incorrect."; other users' edits are unchanged); tenant creation takes an optional admin password (at least 8 characters) and shows a server-generated one once in a copyable dialog without storing it; the fleet categorization error codes (`CategorizationCaptainRequired`, `CategorizationCaptainNotFound`) have labels and translations. - Typed errors instead of message text: MCP authorization refusals return `McpToolError` `Forbidden`; `POST /api/v1/restore` with a file that is not an Armada backup is 400 (`BackupValidationException`, was 500); WebSocket `command.error` replies carry a `code` (`WebSocketCommandErrorCodeEnum`, additive); `mission.status_changed` events carry `Status` / `PreviousStatus` in `Payload` (WebSocket `status` / `previousStatus`); vessel import codes `CategorizationCaptainRequired` / `CategorizationCaptainNotFound` (`VesselImportCategorizationCodes`); fleet action `Data: {Code: UnknownTemplateVariable, VariableName}`; captain model validation `Data: {Reason, Message}` (MCP `Code` = reason); new exceptions `ListenerBindException` (MCP bind), `GitDirtyCheckoutException`, `CaptainNotIdleException`, `DockProvisioningException`; `RemoteTunnelStatus.LastErrorCode`.

## v0.3.0

### Added

- **Multi-tenant support** -- all operational data (fleets, vessels, captains, missions, voyages, docks, signals, events, merge entries) is scoped by tenant
- **Tenant, user, and credential models** -- `TenantMetadata` (`ten_` prefix), `UserMaster` (`usr_` prefix), `Credential` (`crd_` prefix)
- **Bearer token authentication** -- 64-character random alphanumeric tokens linked to a specific tenant and user, sent via `Authorization: Bearer <token>` header
- **Encrypted session tokens** -- AES-256-CBC self-contained tokens with 24-hour lifetime, sent via `X-Token` header. No server-side session storage required
- **Authentication endpoints** -- `POST /api/v1/authenticate`, `GET /api/v1/whoami`, `POST /api/v1/tenants/lookup`
- **Onboarding endpoint** -- `POST /api/v1/onboarding` for self-registration (gated by `AllowSelfRegistration` setting)
- **Tenant CRUD endpoints** -- `GET/POST/PUT/DELETE /api/v1/tenants` (admin only, with self-read for non-admins)
- **User CRUD endpoints** -- `GET/POST/PUT/DELETE /api/v1/users` (admin only, with self-read for non-admins)
- **Credential CRUD endpoints** -- `GET/POST/PUT/DELETE /api/v1/credentials` (admins: all; non-admins: own credentials)
- **Admin vs non-admin access patterns** -- three-tier authorization: `NoAuthRequired`, `Authenticated`, `AdminOnly`
- **Default data seeding** -- on first boot, creates default tenant, user (`admin@armada` / `password`), and credential (bearer token `default`)
- **React dashboard** -- standalone React dashboard (`Armada.Dashboard`) as a separate deployment option for Docker/production
- **Docker Compose with dashboard** -- `compose.yaml` runs `armada-server` and `armada-dashboard` containers together
- **SQL Server support** -- added SQL Server as a database backend option alongside SQLite, PostgreSQL, and MySQL
- **`AllowSelfRegistration` setting** -- controls whether `POST /api/v1/onboarding` is enabled (default: `true`)
- **`SessionTokenEncryptionKey` setting** -- AES-256 key for session token encryption (auto-generated if not provided)

### Changed

- All REST API endpoints now require authentication (except health check, authenticate, tenant lookup, onboarding, and dashboard routes)
- All operational database queries are tenant-scoped for non-admin users
- Admin users see all data across all tenants
- CORS headers now include `Authorization` and `X-Token` in `Access-Control-Allow-Headers`

### Deprecated

- **`X-Api-Key` header** -- retained for backward compatibility but deprecated. When configured, the server creates a synthetic admin tenant (`ten_system`) and user (`usr_system`). Migrate to bearer tokens for new integrations
