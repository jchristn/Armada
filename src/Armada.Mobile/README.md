# Armada Mobile

The Armada app for iPhone, iPad, and Android phones and tablets: React Native with Expo SDK 57 (Expo Router,
TypeScript strict, Hermes). It is a thin client over the Admiral's REST API and WebSocket, like the web dashboard,
and shares the dashboard's API client, models, i18n catalog, and pure logic instead of copying them. The plan,
workstreams, and parity rules are in [`MOBILE_APP_PLAN.md`](../../MOBILE_APP_PLAN.md).

Status: foundation (W0). Sign-in, server profiles, the adaptive navigation shell, the live socket, the in-app
notification center, and the Approvals badge work; every other dashboard screen is a placeholder that names the
workstream that brings it and can open the same page on the web dashboard.

`node_modules`, `ios/`, and `android/` are never committed: the native projects are generated by
`npx expo prebuild` from `app.config.ts` and config plugins.

## Running

The app uses native modules beyond Expo Go (secure store, local authentication, notifications), so run a
development build:

```bash
npx expo run:ios                       # builds, installs on a simulator, starts Metro
npx expo run:ios --device "iPad Air 11-inch (M4)"
npx expo run:android                   # boots/uses an emulator (for example the Armada_Phone AVD)
npx expo run:ios --configuration Release --no-bundler      # embedded bundle, no Metro
npx expo run:android --variant release --no-bundler
```

Connect to an Admiral on first launch: enter its URL (`https://...`, or `http://` on a trusted LAN). From the iOS
simulator the host machine is `127.0.0.1`; from the Android emulator it is `10.0.2.2`. Plain HTTP is allowed for
LAN Admirals (iOS ATS local networking; Android cleartext) and the app warns on every `http://` profile.

## End-to-end tests (Maestro)

```bash
scripts/mobile/run-e2e.sh --platform ios        # iPhone 17 simulator by default (--device NAME)
scripts/mobile/run-e2e.sh --platform android    # Armada_Phone AVD by default (--avd NAME)
scripts/mobile/run-e2e.sh --platform both --no-server-build
```

The script builds `Armada.Server`, starts a throwaway Admiral on `127.0.0.1:44010` with `ARMADA_DATA_DIR` in a
temp directory (never `~/.armada`), builds and installs a Release build of the app, and runs the flows in
[`e2e/`](e2e): add the server, sign in as `admin@armada` with the default password, take "Skip for now" on the
password-change screen, land on Ask, walk the tabs and a few routes, switch the theme, and sign out. Reports and
screenshots go to the `--output` folder (printed at the end). It stops everything it started.

## How the code is shared with the dashboard

```
src/Armada.Dashboard/src/          shared, imported as @dashboard/...
  api/client.ts                    the REST client; configureClient({ baseUrl, platform }) makes it host-agnostic
  types/models.ts                  API models
  lib/**                           pure logic (navModel, notificationEvents, inboxSummary, armadaSocket, ...)
  i18n/catalog.ts                  catalog types, translation, locale normalization, formatting
src/Armada.Server/wwwroot/i18n/    armada.json, bundled at build time as @armada-i18n/armada.json
```

- [`sharing.config.js`](sharing.config.js) is the single list of shared folders and the few dashboard-only `lib`
  modules (browser hooks such as `useTablePrefs`). Metro, Jest, ESLint, and the shared-module test read it.
- Shared modules must not use `window`, `document`, `localStorage`, `navigator`, `import.meta`, or `react-dom`.
  `npm run lint:shared` lints the dashboard's shared folders against that contract, and
  `src/__tests__/sharedModules.test.ts` imports every shared module under React Native.
- Metro watches the dashboard folders and resolves bare imports made by shared files (`react`) from this project,
  so only one React is bundled. TypeScript maps `react` the same way (`tsconfig.json`).
- A dashboard change to a shared module is a mobile change too: CI runs both suites.

## Routes, placeholders, and parity

- `python3 scripts/mobile/generate-route-screens.py` regenerates `src/navigation/dashboardRoutes.generated.ts` from
  `App.tsx` and creates a screen for any new dashboard route (a placeholder, or a redirect for a dashboard
  redirect). It never overwrites an existing screen; replace placeholders with real screens freely.
- `python3 scripts/mobile/generate-parity-manifest.py` regenerates `parity.json`; statuses, screens, workstreams,
  and notes are edited by hand once an entry exists. Mark an entry `implemented` when its screen ships.
- `npm run routes:check` and `npm run parity:check` run in CI. The parity check fails on missing or extra entries;
  from W6 CI adds `--forbid-planned` so nothing may remain planned.

## Builds and store submission (EAS)

`eas.json` has `development` (simulator / APK), `preview` (internal distribution), and `production` (store)
profiles. Before the first cloud build the maintainer must:

1. Replace the placeholder bundle id `com.armada.mobile` in `app.config.ts` (or set `ARMADA_MOBILE_BUNDLE_ID`).
2. Run `npx eas-cli init` and set `ARMADA_MOBILE_EAS_PROJECT_ID` (or put the id in `app.config.ts`).
3. Fill in the `submit.production` placeholders in `eas.json` (Apple ID, App Store Connect app id, team id) and
   provide the Google Play service account key at `secrets/google-play-service-account.json` (ignored by git).

## Push notifications

The app registers its Expo push token with each signed-in server (`POST /api/v1/push/devices`, see
[REST_API.md](../../docs/REST_API.md#push-notifications)), keeps the returned `pdv_` device id per profile in secure
storage, re-registers when the token changes, and deletes the device on sign-out and profile removal. Permission is
asked from a one-time sheet after sign-in (or from Preferences), never at launch. Preferences lists the server's
categories as switches and can send a test push. Taps open the pushed dashboard path after validating it; Approve and
Deny (iOS category `armada_approve_deny`, Android action buttons) require an unlocked device and, for profiles with
biometric unlock, Face ID / Touch ID / fingerprint before the decision is sent. The app badge is the Approvals count.

Real delivery needs credentials the maintainer owns: an EAS project id (`ARMADA_MOBILE_EAS_PROJECT_ID`), an APNs key
for iOS, and an FCM (Firebase) configuration for Android, all attached through `eas credentials`. Without the project
id the app works normally and Preferences says that push is not configured for the build. To try a notification on the
iOS simulator without any of that, push an APNs payload (Expo puts the data object under `body`):

```bash
cat > /tmp/armada-push.apns <<'JSON'
{"Simulator Target Bundle": "com.armada.mobile",
 "aps": {"alert": {"title": "Approval needed", "body": "Dispatch a mission"}, "category": "armada_approve_deny", "badge": 1},
 "body": {"url": "/missions/msn_example", "kind": "failed", "entityId": "msn_example", "category": "MissionFailed"}}
JSON
xcrun simctl push booted com.armada.mobile /tmp/armada-push.apns
```

## Armada.Proxy profiles

Choose **Armada.Proxy** when adding a server to reach an Admiral through a remote-access proxy: sign in with the
proxy password (a challenge and SHA-256 proof, never the password itself), pick a connected Admiral, then sign in to
that Admiral as usual. The proxy session token is kept in secure storage and sent as `X-Armada-Proxy-Session` on
relayed requests, as `Authorization: Bearer` on `/proxy-api`, and on `/ws` as an `armada-proxy-session.<base64url>`
subprotocol (falling back to the header if the subprotocol is refused). When the 24-hour proxy session ends, the app
asks only for the proxy password and returns to the same Admiral with the stored Admiral session. The sequence is in
[REMOTE_SERVER.md](../../docs/REMOTE_SERVER.md#native-clients-through-armadaproxy).
