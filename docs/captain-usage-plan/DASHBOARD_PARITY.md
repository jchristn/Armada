# Account usage: dashboard, TUI and mobile parity

Phase 5 (AC5) ships the account usage surfaces in the React dashboard. This file
records the reviewed parity decisions for the TUI (`src/Armada.Tui/parity.json`)
and mobile (`src/Armada.Mobile/parity.json`) manifests. Both manifests are
generated by `scripts/tui/generate-parity-manifest.py` and
`scripts/mobile/generate-parity-manifest.py` from the dashboard `api/client.ts`
section `// ==================== Usage ====================`.

## Client calls

| Dashboard export | Route | TUI (ArmadaClient) | Mobile |
|---|---|---|---|
| getUsageLatest (captainId, or captainIds batch) | GET /api/v1/usage/latest | GetUsageLatestAsync (single captain filter only, see below) | planned |
| getUsageSnapshots | GET /api/v1/usage/snapshots | GetUsageSnapshotsAsync | planned |
| getUsageSeries | GET /api/v1/usage/series | GetUsageSeriesAsync | planned |
| getUsageMissions | GET /api/v1/usage/missions | GetUsageMissionsAsync | planned |
| captureCaptainUsage | POST /api/v1/captains/{id}/usage/capture | CaptureCaptainUsageAsync | planned |

The routes are frozen in `docs/api-surface-1.0.json`; no
`_DashboardRequestsPendingServer` entry is needed.

## Reviewed exceptions

1. TUI screens. The TUI has typed `ArmadaClient` methods for every usage read and
   for capture now, so the manifest entries are `implemented` at the client level,
   but no TUI screen renders account limits yet. Reason: Phase 5 is scoped to the
   dashboard (CAPTAIN_USAGE_PLAN.md phase table); a TUI usage view needs its own
   TUIKit layout and parity cases. The manifest notes name this exception.
2. Batch latest from Armada.Client. `ArmadaClient.UsagePath` serializes
   `UsageQuery` properties with `Convert.ToString`, so a `CaptainIds` list would
   not become a comma-separated `captainIds` value. The dashboard batch read
   (`getUsageLatest({ captainIds })`) has no working ArmadaClient equivalent; the
   TUI only needs the single-captain read.
   Fixing the client is outside the dashboard slice.
3. Mobile. The mobile app has no usage screen. Entries stay `planned` under
   workstream W3.2 (the Captains workstream) with a note pointing here; the mobile
   generator's `AREA_WORKSTREAMS` maps the `Usage` area to W3.2.

## Dashboard surfaces

- Captains table: Usage column (one batch latest request per 100 visible ids)
  and the row ActionMenu item `View Usage`, which opens
  `/captains/{id}?section=usage` for every captain state.
- Captain detail: Usage section (`#captain-usage`), Capture now, capture settings.
- Token usage (`/activity`): Overview and Limits tabs next to the existing Tokens tab.
- Settings: server-wide Usage capture panel (GlobalAdmin; read-only explanation otherwise).
