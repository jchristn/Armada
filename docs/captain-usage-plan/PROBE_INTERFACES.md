# Phase 0: runtime usage interfaces

This document is the AC0 evidence for `CAPTAIN_USAGE_PLAN.md` phase 0. It records what each of the
eight runtimes in `AgentRuntimeEnum` actually exposes for account-limit reading on the inspecting
host, what Armada already sees passively, and which interfaces are unavailable. It changes no
product behavior: every capture adapter described by the plan stays disabled until its evidence row
says otherwise.

The named check for this document is `Usage.InterfaceEvidence`, a shared Touchstone suite
(`src/Test.Shared/Suites/Runtimes/UsageInterfaceEvidenceSuite.cs`). It asserts that all eight
runtimes carry the required evidence fields below, that every fixture in
`src/Test.Shared/Fixtures/Usage/` is inventoried, and that no fixture claims to be verified unless
it was actually observed on this host.

### ClaudeCode

- Runtime: ClaudeCode
- Binary: `claude`, a native Mach-O arm64 executable installed through `~/.local/share/claude/versions/2.1.316`.
- Version: 2.1.316.
- Host OS: macOS 26.6 arm64.
- Auth mode: not inspected. The inspecting shell had no API-key or OAuth-token environment variable.
  `claude auth status` is the read-only local report, but it reads the local credential store, so it
  is an operator opt-in and was not run. `claude --help` states that `--bare` mode authenticates
  strictly with `ANTHROPIC_API_KEY` or `apiKeyHelper` and never reads OAuth or the keychain, which
  is why a subscription session cannot be distinguished without that opt-in check.
- Interface: passive stream events plus one undocumented active candidate.
  1. Passive: `--print --output-format=stream-json` emits `rate_limit_event` lines with a
     `rate_limit_info` object. Armada already parses these (`ClaudeRateLimitEvent`,
     `ClaudeRateLimitInfo`), formats them in `RuntimeLogFormatter`, and deliberately keeps them out
     of mission transcripts in `ClaudeMissionStreamDecoder`. Fields are `status`, `resetsAt`,
     `rateLimitType`, `utilization`. The event is only produced while a real mission runs, so this
     is a free harvest source for phase 3 and not an independent poll.
  2. Active candidate: an undocumented OAuth usage endpoint. The installed 2.1.316 binary contains
     the literal `api/oauth/usage` together with the window name strings `five_hour`, `seven_day`,
     `seven_day_opus` and `seven_day_sonnet`. This corroborates the plan's candidate endpoint and
     window names, and nothing more: it does not prove that the endpoint accepts the CLI's token,
     what headers or scopes it needs, or that its response uses those names as keys.
  3. PTY `/usage`: the interactive slash command. It is official UI but an undocumented scrape, it
     does not operate in `-p` mode, and it must never be sent as a model prompt. Separate explicit
     opt-in only.
- Fields: passive event gives a percentage fraction and a window name. The active endpoint is
  expected to give per-window utilization percentages and reset times; unverified.
- Timestamps: `rate_limit_info.resetsAt` is absolute Unix epoch seconds. The `/usage` terminal text
  is human-formatted local time and would need normalization to UTC; do not parse it as a machine
  timestamp.
- Permissions: reading the endpoint needs no model tool permission, only whatever the local
  credential store already grants the CLI. Whether the endpoint accepts that credential without
  additional consent is unverified, so it stays `Undocumented`.
- Confidence: Undocumented for the endpoint, Official for the interactive UI, Official for the
  harness stream shape.
- Fixtures: `claude-rate-limit-event.sanitized.jsonl`.
- Next step: replace the passive fixture with a live `rate_limit_event` captured from a real
  mission, and obtain an authenticated, opt-in reading of the usage endpoint before enabling the
  adapter.

### Codex

- Runtime: Codex
- Binary: `codex` (`codex-cli`), installed as a user binary.
- Version: 0.163.0.
- Host OS: macOS 26.6 arm64.
- Auth mode: not inspected. `codex login status` is the read-only report and `codex login
  --with-api-key` reads a key from stdin; neither was run. No `OPENAI_API_KEY` was present in the
  inspecting shell.
- Interface: a local `codex app-server` JSON-RPC session over stdio (`--listen stdio://` is the
  default) that is initialized with `clientInfo` and then answers
  `account/rateLimits/read`. No thread or turn is created. This is verified from the schema bundle
  generated by the installed binary, not from a live session.
  - `initialize` params require only `clientInfo {name, title?, version}`. `capabilities` is
    optional and `experimentalApi` defaults to false. `account/rateLimits/read` appears in the
    generated client request union without an experimental gate, so the probe needs no
    experimental capability.
  - `account/rateLimits/read` returns `rateLimits` (a single backward-compatible snapshot),
    `rateLimitsByLimitId` (map keyed by metered `limit_id`, for example `codex`), a nullable
    `accountId`, nullable `ordinaryUsageAllowed`, `rateLimitResetCredits {availableCount,
    credits[]}` and an optional backend-owned `rateLimitUpsell` banner.
  - A snapshot has nullable `limitId`, `limitName`, `normalModelSlug`, `planType`,
    `rateLimitReachedType`, `spendControlReached`, `credits {hasCredits, unlimited, balance}`,
    `individualLimit {limit, remainingPercent, resetsAt, used}`, and nullable `primary` and
    `secondary` windows.
  - A window has required `usedPercent` (int32) plus nullable `windowDurationMins` (int64) and
    nullable `resetsAt` (int64). Because the duration is data, neither window may be assumed to be
    5 hours or 7 days.
  - `Account/rateLimits/updatedNotification` pushes the same snapshot during an app-server session,
    which is a free passive source whenever Armada already holds such a session.
- Fields: utilization percent per window, window duration, per-model or per-limit identifiers,
  plan type, credit balance, spend-control state.
- Timestamps: `resetsAt` is absolute Unix epoch seconds; `windowDurationMins` is a duration, not a
  timestamp. Any relative `resets_in_seconds` variant belongs to older session-log formats and must
  be converted from the event time, never from polling time.
- Account identity: the response can carry `accountId`. Phase 1 requires HMAC-ing it on the
  credential host and never persisting the raw value, so the sanitized fixture sets it to null.
- Not verified: the local session-log fallback (`~/.codex/sessions/**/*.jsonl` records containing
  rate limits). The installed `codex exec --json` prints JSONL events, but the generated schema does
  not describe those files and no rate-limit record was observed here. It stays `Undocumented`.
- Confidence: Official for the app-server interface.
- Fixtures: `codex-account-ratelimits-read.sanitized.json`, `codex-app-server-initialize.sanitized.json`.
- Next step: run one opt-in `initialize` plus `account/rateLimits/read` exchange on the credential
  host and store only the sanitized snapshot.

### Gemini

- Runtime: Gemini
- Binary: not installed on this host (`gemini --version` fails).
- Version: unknown.
- Host OS: macOS 26.6 arm64.
- Auth mode: not applicable; no `GEMINI_API_KEY` in the inspecting shell.
- Interface: none verified. The plan's `/stats` reference is session accounting, not remaining
  capacity. The only quota signal Armada currently recognizes is the provider exhaustion error
  (`RESOURCE_EXHAUSTED`, handled by `RuntimeProviderErrorParser`); it carries no reliable reset
  value, so no reset or 100 percent reading may be invented from it.
- Fields: none authoritative. Derived percentage only when an operator configures a budget with a
  matching counter unit and a reset timezone.
- Timestamps: none from a generic error body. A configured budget boundary is an Armada estimate.
- Confidence: Unavailable for account limits, Estimated for configured budgets.
- Fixtures: `gemini-resource-exhausted.sanitized.json` (error shape only).
- Next step: recheck if Google publishes a read-only quota endpoint for the installed CLI; until
  then Gemini stays estimated and cannot quarantine a captain.

### Mux

- Runtime: Mux
- Binary: `mux`, installed as a dotnet tool.
- Version: v1.5.0.
- Host OS: macOS 26.6 arm64.
- Auth mode: not inspected; mux authenticates through its own endpoint configuration
  (`endpoints.json`), which Armada does not read.
- Interface: `mux --print --output-format jsonl --stats` reports per-run usage. `mux --help` and
  `mux run --help` document `--stats` and `--no-stats`, and the CLI dispatch lists only `probe`,
  `endpoint`, `export`, `plugin`, `worktree`, `mirror` and `mcp serve`: there is no standalone
  stats or usage subcommand, which confirms the plan's note.
- Fields: the `run_completed` usage object, parsed by Armada's `MuxRunUsage`: `inputTokens`,
  `outputTokens`, `cachedTokens`, `reasoningTokens`, `totalTokens`, `estimatedTokens`, `costUsd`
  (all nullable). This is accounting for the run that just happened, never a remaining quota.
- Timestamps: the usage object has no timestamps; the run completion event time is the observation
  time.
- Header seam: mux owns the provider HTTP transport, so Armada cannot see provider rate-limit
  response headers unless mux surfaces them in its structured output, and contract v2 usage does
  not. Provider headers from Mux are therefore `Unsupported` from Armada's side.
- Confidence: Official for the stats flags, Undocumented for the output parser, Unavailable for
  account limits.
- Fixtures: `mux-run-completed-usage.sanitized.json`.
- Next step: keep per-run usage accounting and do not probe mux for quota.

### ApiEndpoint

- Runtime: ApiEndpoint
- Binary: none, an in-process PolyPrompt tool-calling loop (`ApiAgentRuntime`).
- Version: PolyPrompt 3.5.0 (`Armada.Core.csproj`).
- Host OS: macOS 26.6 arm64.
- Auth mode: per `ModelEndpoint` configuration (`ProviderDefault`, bearer, basic, custom header,
  query parameter, access proxy) applied by `ModelEndpointAuthHandler`.
- Interface: passive response headers only. `ModelEndpointClientFactory.CreateCompletion` builds
  the provider client with `ModelEndpointAuth.CreateHttpClient(endpoint)`, which returns an
  `HttpClient` wrapping `ModelEndpointAuthHandler` over the shared handler. A phase 3
  `UsageRateLimitHandler` belongs in that chain, because `CompletionClientBase` in PolyPrompt is
  not expected to hand back a raw `HttpResponseMessage`.
- Known seam gap: `ModelEndpointAuth.CreateHttpClient` returns null when `AuthType` is
  `ProviderDefault` and the endpoint declares no extra headers. In that case PolyPrompt constructs
  its own transport and an Armada handler would never see the response. The phase 3 insertion point
  must therefore cover that default path, not only the configured-auth path.
- Fields: `anthropic-ratelimit-requests-*`, `anthropic-ratelimit-input-tokens-*`,
  `anthropic-ratelimit-output-tokens-*`, `anthropic-ratelimit-tokens-*`, `x-ratelimit-*` and
  `retry-after`, limited to the allowlist in the fixtures. Absence of headers is `Unsupported`, not
  `AuthMissing`.
- Timestamps: Anthropic reset headers are RFC 3339 timestamps; OpenAI-style `x-ratelimit-reset-*`
  values are duration strings such as `6m0s`, and `retry-after` is delay seconds. Converted values
  must stay relative to the response observation time.
- Not verified: that streamed responses and streamed error responses pass through the same handler
  before the body stream is disposed, and that every selectable provider uses this client path.
  Both are phase 3 acceptance checks with an attached capture before a known request.
- Confidence: Official for the header names, Unavailable until a response is observed and captured.
- Fixtures: `anthropic-ratelimit-headers.sanitized.json`,
  `openai-compatible-ratelimit-headers.sanitized.json`.
- Next step: add a capture fixture taken from a known request through the Armada transport before
  enabling passive header capture.

### Custom

- Runtime: Custom
- Binary: none on this host; the operator supplies an executable plus an argument array.
- Version: contract `schemaVersion` 1.
- Host OS: macOS 26.6 arm64.
- Auth mode: whatever the executable already has as the Harbor service user; Armada passes no
  credentials.
- Interface: a single stdout JSON object of at most 64 KiB, defined by the plan. Tenant
  administrators on permitted hosts only, no shell interpolation, stderr never becomes a Jobs log.
- Fields: `schemaVersion`, `status`, `accountKey`, `provider`, `capturedUtc`, `source` and up to 32
  bounded `windows` with `name`, nullable `usedPercent`, `used`, `limit`, `unit`,
  `windowMinutes` and nullable `resetsUtc`.
- Timestamps: `capturedUtc` is the observation time; each window `resetsUtc` is an absolute UTC
  reset. Skew beyond the configured allowance is rejected.
- Confidence: Undocumented unless separately verified; the host still owns the final account HMAC
  and the allowed source and status.
- Fixtures: `custom-usage-contract.sanitized.json`.
- Next step: the phase 3 validator must treat unknown schema versions, NaN or infinity, negative
  counts, impossible percentages and non-positive limits as failures.

### Pi

Pi (`AgentRuntimeEnum.Pi`) was added to the enum after `CAPTAIN_USAGE_PLAN.md` was written, so it is
outside the AC0 list of eight and is not covered by this evidence. It remains a normal captain
runtime with no usage capture adapter, and the disabled framework must not depend on it.

## Answers to the phase 0 open questions

| Question | Answer from this inspection | Residual risk |
|---|---|---|
| Is the installed Claude OAuth client permitted to read its usage endpoint? | Unproven. The endpoint path and window names exist in the 2.1.316 binary, but permission, request shape and response shape need an opt-in authenticated read. | The endpoint may refuse or change without notice. |
| Which credential profile selectors identify shared accounts? | Not answered. Claude exposes only `auth status` locally, Codex exposes `account/read` and a nullable `accountId`, and neither was called. | Account identity stays host-local and HMAC-derived in phase 1. |
| Does current Codex exec emit limit events? | Unproven for exec. The app-server `account/rateLimits/read` request and the `account/rateLimits/updatedNotification` push are verified from the installed schema. | The session-log fallback stays undocumented and disabled. |
| Where can ApiEndpoint and Mux HTTP headers be observed before stream disposal? | ApiEndpoint: in a DelegatingHandler around the PolyPrompt transport, with the ProviderDefault gap noted above. Mux: not observable by Armada at all. | Phase 3 needs an attached capture proving headers are seen before disposal. |
| Gemini budget counters and model bucket mappings | Not available. Only an operator-configured budget estimate and an exhaustion error. | Estimation stays labeled and cannot quarantine. |
| Cost currencies | Only mux `costUsd` is defined; everything else is null or estimated. | No conversion, no subscription charge claims. |

## Effect on the disabled framework

Nothing in this evidence enables an adapter. Unverified details stay `Unsupported`,
`Estimated`, `AuthMissing` or `Unavailable`, all of which are inert for routing. Token recording,
existing token charts, mission routing, launch slots and every default (`UsageCaptureEnabled`
false, interval 300, mode Auto) are unchanged by phase 0.
