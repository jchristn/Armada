# Exclusive captain session ownership validation

Planning and backlog refinement now reserve captains atomically before provisioning/activation. Claims serialize with mission-slot acquisition on the captain row and require zero execution slots. The same session can recover its reservation without losing its runtime fields; recovery may adopt a legacy unowned Planning/Refining state. A different owner or running mission refuses the claim. All four providers delegate to the shared conditional SQL implementation; no schema migration is needed because migration 118 already introduced current_session_id.

Runtime updates and release match the session id. Failed creation, cancellation cleanup, stale stops and late callback writes cannot release or overwrite a newer owner. Ordinary captain updates cannot acquire/erase exclusive ownership or replace its runtime fields; legacy state-only reservation release cannot release a session owner. Session-scoped stop uses the old session's process only while ownership still matches. A process returned after ownership is lost gets a best-effort stop by its own PID. Recovery fails an obsolete session with an ownership explanation while preserving current work. Waiting diagnostics follow the actual session owner, with private session details omitted.

## Manual validation

Create a planning session on a captain with maximum concurrency greater than one. Attempt a refinement session or mission assignment on the same captain: no execution slot may be admitted while planning owns it. End planning and try again; the captain should be available. Repeat with refinement. Repeat a stop on an older session after starting a replacement and confirm the replacement remains active. Restart with an active or responding session and verify recovery retains the correct owner. A session whose ownership changed must fail recovery with an explanation rather than take over another session/mission.
