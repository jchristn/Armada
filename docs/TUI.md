# Armada TUI

The Armada TUI is the web dashboard in a terminal. It talks to the same Admiral over the same REST API and WebSocket, enforces nothing the server does not, and is meant for people who live in a shell, work over SSH, or are on a machine without a browser. It ships inside the `armada` CLI, so one install gives you both.

This page covers what exists today: installing and starting it, server profiles, signing in, getting around, Ask Armada, the Approvals center, notifications, the Operations screens (Home, Needs You, Planning, Dispatch, Backlog, Fleet Actions, Missions, Voyages, Merge Queue, and Jobs), the Build screens (Vessels, the import wizard, Vessel Health, the vessel page and onboarding, Fleets, the Workspace, Captains, and Docks), the Delivery, Configuration, Activity, and System screens, the keys, and troubleshooting. Ask Armada is the screen the TUI opens into. Every dashboard route now opens a real screen; progress on the remaining quality and documentation work is tracked in `TUI_APP_PLAN.md`.

## Install and start

Install Helm the way you normally do, then run the commands below. `armada tui` is in every Helm package: the .NET tool (`dotnet tool install -g Armada.Helm`, which the `scripts/*/install` scripts also use) and the Linux `.deb` and `.rpm` CLI packages. The macOS `.pkg`, Windows `.msi`, Harbor installers, and the Docker image carry the server or Harbor, not the CLI.

```
armada tui
armada tui --server http://127.0.0.1:7890
armada tui --profile work
armada tui --server https://armada.example.com --profile prod --route "/missions?tab=voyages"
```

With no options the TUI connects to the last profile you used, or to the local Admiral from your Armada settings. `--server` connects to a URL and remembers it as a profile named after the host. `--profile NAME` picks a saved profile (and, combined with `--server`, creates or updates it). `--route` chooses the first screen after sign-in; otherwise you land on the screen you left, and on a first run you land in Ask Armada.

For scripted starts, `ARMADA_URL` supplies the server and `ARMADA_TOKEN` a session token or API key, which skips the login screen when the server accepts it.

The terminal needs to be at least 80 columns by 24 rows. Below that the TUI shows a "terminal too small" screen with the size it needs and the size it has (Ctrl+Q still quits) and comes back when you resize. It works in Windows Terminal, iTerm2, kitty, WezTerm, Ghostty, Alacritty, GNOME Terminal, and inside tmux and SSH sessions. Terminal.app and legacy conhost run with fewer mouse and key features.

## Profiles, preferences, and credentials

Preferences live in `~/.armada/tui.json`: server profiles (name, URL, last user, last tenant, last login method), theme, language, sidebar and dock state, the last route, per-table column and page-size choices, auto-refresh intervals, notification settings, and key rebindings. The file never holds a secret. Set `ARMADA_TUI_PREFERENCES` to use another file, which is how the tests keep away from your home directory.

Session tokens and API keys are stored per profile in the operating system's credential store: the macOS Keychain (through `/usr/bin/security`), Windows Credential Manager, or libsecret on Linux (through `secret-tool`). When none of those is available, or a keychain write fails (a locked keychain over SSH, for example), the token goes to `~/.armada/tui-credentials.json`, created with mode 0600. `ARMADA_TUI_CREDENTIAL_STORE` forces a store (`file`, `keychain`, `wincred`, or `secret-tool`) and `ARMADA_TUI_CREDENTIALS` moves the file.

You can switch servers from the login screen's Server picker (which also has "Add server...") or from File, Switch server profile. The profile created on first start follows the local Admiral's port from `settings.json` until you edit its URL. In the Server picker, `e` (or `E`) edits the highlighted server's name and URL; saving an edit to the server you are on reconnects the login screen to the new URL. While editing is available, `e` edits instead of filtering.

## Signing in

The login screen mirrors the dashboard. Email Login asks for your email, looks up your tenants, shows a tenant picker when more than one matches, and then asks for the password. API Key Login takes a session token, a credential's bearer token, or the Admiral API key; the TUI tries it as `X-Token`, then as a bearer token, then as `X-Api-Key`, and validates it with `whoami`. `F2` switches between the two modes, and `Ctrl+R` shows or hides a masked password or key. `Tab` and `Shift+Tab` move through the card top to bottom (Server, login mode, the current field, the buttons, Language, Theme) and wrap; the current field has focus when the screen opens. The language and theme pickers work before you sign in, and the screen shows the default credentials (`admin@armada` / `password`) for a fresh install.

A stored token is reused on the next start. If the server later answers 401, the TUI returns to the login screen with "Your session expired. Sign in again." File, Sign out forgets the stored token.

When the server is on this machine (localhost, 127.0.0.1, or ::1), the login screen is prefilled for a local install: the email is `admin@armada` (or the last account used with that profile), the password is `password` until the profile has signed in once, and API Key Login holds the `apiKey` from the local `settings.json` when the profile points at the local Admiral's port. The prefilled password and key start selected (shown highlighted): press Enter to use them, or just type, and what you type replaces the prefill instead of being appended to it. Backspace clears the prefill, and an arrow key, Home, or End keeps it for editing. A new install's default profile uses the `admiralPort` from that `settings.json`. A remote server gets no prefill. The Server picker opens wider than the other pickers so long URLs fit.

The TUI does not force a password change; this is the intended policy, not a gap. Signing in with the default password goes straight to Ask Armada (or your `--route`), and the header shows a warning while default credentials are in use. The dashboard, by contrast, blocks everything until the default password is changed. Change the password (dashboard, or Users in the TUI) before exposing the server beyond localhost; the Admiral refuses to listen on a non-loopback address while default credentials are in use.

While the server reports default credentials in use (an `admin@armada` account somewhere still has the default password, or the default bearer token is active), administrators see a warning line under the header on every screen. It goes away when the last default credential is changed.

## Getting around

The screen is a header, a menu bar, the sidebar, the main area, an optional Ask dock, and a status bar. The header shows the tenant, your email, your role (Global Admin or Tenant Admin), server health, whether the WebSocket is live, running background jobs, pending approvals, and the notification bell with its unread count. Every state is written out in text, so nothing depends on color. When you are connected through Armada.Proxy, a second header line shows the proxy instance, and File has Switch Deployment and Proxy Logout.

The sidebar has the same sections, labels, and order as the dashboard, with the Needs You count beside Needs You (marked `!` when something is critical). Below 110 columns it collapses to one-letter icons, and below 90 it hides; `Ctrl+B` brings it back. Sections fold with Left and Right.

There are three ways to reach anything, and they work everywhere:

- the menu bar (`F10`), where the Actions menu always lists the current screen's actions;
- the command palette (`Ctrl+K`), which fuzzy-matches every destination, every hub tab, and every command, and opens an entity directly when you type its id (`msn_...`, `vsl_...`, `vyg_...`, `cpt_...`, and so on);
- the go-to keys: `g` followed by a letter.

The palette runs commands, not just navigation, so "theme light" or "toggle sidebar" work from it. Hubs (Missions, Delivery, Vessels, Captains, Configuration, Activity, Settings, Dispatch, Fleet Actions) show their tabs across the top, and the active tab is part of the route, which is why deep links such as `/vessels/health?overall=Fail` and Back and Forward behave.

Toasts appear at the top right for mission, voyage, captain, deployment, backlog item, and incident changes, with the dashboard's wording and severity (for example `Mission "Fix tables" - Landed` as a success, `Captain "claude-1" - Stalled` as a warning). Each one is also kept in the notification history with a link to the item. `Ctrl+O` runs the newest toast's action (usually Open). `Ctrl+N` opens the notification center: the latest 100 notifications, kept between runs, with `m` to mark all read and `x` (twice) to clear. The terminal bell rings for failures and approvals, and setting `OsNotifications` in `tui.json` (`Osc9`, `Osc777`, or `Native`) raises an OS notification while the terminal is not focused.

Lists use a shared grid: sized columns, server-side sorting with `^` and `v` indicators, multi-select for bulk actions, a column chooser, and a paging bar that reads "Showing 1-25 of 248. Page 1 of 10." Background refreshes never move your cursor.

## Ask Armada

Ask Armada is where the TUI starts and where most of the work happens. It is the dashboard's Ask page laid out for a terminal: the conversation list on the left, the open conversation on the right, and the composer at the bottom. Everything lives in one session object, so you can jump to another screen and come back to the same conversation, the same draft, and a reply that kept streaming while you were away.

The conversation list searches on the server as you type (after a short pause), keeps pinned conversations on top and the rest by their latest message, and marks each row with its unread count, `* Working` while work it started is still running, `Replying...` while the captain is answering, and an `[Archived]` tag when archived ones are shown (`A` toggles them). `Enter` opens a conversation, `n` starts a new one, `/` searches, `e` renames in place, `p` pins, `s` asks for a summary, `Del` deletes after the dashboard's confirmation, and `.` opens the row menu with all of those. The list pages 50 at a time and loads the next page when the cursor reaches "Load more". Below 100 columns the list folds away and `Ctrl+T` brings it back as an overlay. Opening a conversation marks it read, and so does returning focus to the terminal while it is open; nothing is marked read while the terminal is in the background.

The header shows the title (`e` to rename), the captain (`c`, see "Choosing a captain" below), auto-approve (`Ctrl+Y`), Summarize (`s`), and More (`.`). Turning auto-approve on asks first, with the dashboard's warning, and a banner stays across the top of the conversation while it is on. When the captain cannot reach Armada over MCP (its runtime is neither Claude Code nor an API endpoint and it reports no Armada tools) a note says so and links the setup instructions for that runtime. A strip under the header lists the work the conversation is tracking with "N active of M"; `w` jumps to the next item's live card.

The transcript renders every message kind the server writes: your messages, captain replies in Markdown with tool chips (`[ok]`, `[..]` while running, `[x!]` on failure), a collapsed thinking section, the turn's duration, and a metrics line the TUI measures itself (time to first token, approximate tokens and tokens per second, total time). Confirm cards show the tool, who proposed it, the one-line summary, the exact arguments, the expiry, and the outcome once decided. Action results carry the live work card for what they started, progress updates link back to that card, and summaries, errors, and system notes have their own styles. While a reply streams, the Markdown is re-rendered on every chunk, so lists, headings, and code blocks read correctly before the turn ends instead of collapsing onto one line.

`Up` and `Down` move between messages and into the rows of a work card. On a confirm card, `a` approves, `r` rejects, `x` shows the arguments (and the result once it ran), and `y` copies them. On a work card row, `Enter` opens the mission, `o` opens its pull request, `l` shows its log, and `d` its diff. `Enter` on a captain reply expands its tool calls and `t` its thinking; `y` copies a message as Markdown and `Y` the whole conversation. `PgUp` and `PgDn` scroll, `Home` goes to the top and loads earlier messages (30 at a time), `End` returns to the live tail, and `Ctrl+F` or `/` searches with `n` and `N`. When you scroll away from the bottom the transcript stops following and counts the new lines below instead of moving under you.

The composer sends with `Enter` and adds a line with `Shift+Enter` or `Ctrl+J`. `Ctrl+E` opens the draft in `$EDITOR`, `Up` on an empty composer recalls what you sent earlier, and `Esc` moves to the transcript and focuses the newest card waiting for a decision. Your message appears at once and is confirmed or removed when the server answers. Typing `/` opens the quick actions: Dispatch and Fleet action open inline forms with the dashboard's fields and checks (submitting the form is the confirmation), Status and Health run immediately, and Import opens the import screen. While a turn runs, `Ctrl+C` or `Esc` twice stops it; the TUI shows "Stopping..." and settles the turn itself if the server has not confirmed within 8 seconds.

Two shortcuts reach Ask from anywhere. `Ctrl+J` toggles the Ask dock at the bottom of any screen, which shows the tail of the open conversation (streaming included), the pending approval count, and a one-line composer that sends to that conversation. `Alt+A` (Ask about this) opens a new conversation with the current screen's subject already typed, for example `On vessel DemoRepo (vsl_...): `.


### Choosing a captain

The `c` key only works while the conversation has focus, not while you are typing in the message box. When Ask opens, the cursor is in the message box at the bottom, so there `c` just types the letter; the header shows the captain with `[Esc c]` while you are typing and `[c]` once the conversation has focus. To change the captain:

1. With the cursor in the message box, press `Esc`. Focus moves up to the conversation (the transcript above the message box).
2. Press `c`. The captain picker opens; it also lists "No captain (quick actions only)".
3. Pick a captain with the arrow keys (or type to filter) and press `Enter`.
4. Press `Esc` to go back to the message box.

Or, from anywhere: press `Ctrl+K`, type `captain`, and run "Choose captain...". Neither way works while a captain reply is in progress; stop it first (`Ctrl+C`, or `Esc` twice).

## Approvals

`Ctrl+A` opens the Approvals center, a single queue of everything waiting on you, most urgent first. The header shows the count on every screen, a new item rings the terminal bell (and raises an OS notification while the terminal is in the background, when `OsNotifications` is set), and a proposal from a conversation you are not looking at also raises a toast whose `Ctrl+O` action opens that conversation.

| Item | Where it comes from | Keys |
|---|---|---|
| Ask proposal | `ask.proposal` events and open conversations | `a` approve, `r` reject, `x` arguments |
| Mission review | the Needs You inbox and `mission.changed` | `a` approve, `c` conditionally approve, `m` more work required, `d` deny |
| Deployment approval | the inbox and `deployment.changed` | `a` approve, `d` deny |
| Failed landing | the inbox and `mission.changed` | `l` retry landing |
| Stalled captain | the inbox and `captain.changed` | `s` stop, `R` recall, `t` restart |

Every decision makes the same call with the same confirmation as the dashboard screen the item belongs to. Review decisions go through the Resolve Review dialog, where feedback is required for Conditionally Approve and More Work Required. Deployments and captain actions ask first. `Enter` opens the item's own screen and `F5` re-reads the inbox. The queue follows the inbox poll and also reacts to entity events immediately, so a review appears the moment its mission enters Review and disappears as soon as it leaves.

## Lists, forms, and detail pages

The Delivery and Configuration hubs are built (workstreams W5 and W6); their dashboard routes, tabs, and deep links open real screens instead of placeholders. They share one set of conventions, so learning one screen teaches all of them.

A list screen shows the dashboard's overview figures on one line ("Total Deployments 12 | Pending Approval 1 | ..."), then the filter row, then the grid. Filters run on the server wherever the API supports them, and every filter can be deep linked by its key, so `/delivery?tab=deployments&status=PendingApproval` opens the Deployments tab already filtered. `/` jumps into the filter row, `Tab` moves between filters, and `Enter` or `Esc` returns to the grid. Paging asks the server for one page at a time. Sorting by a column (`s` on the focused column, `S` to reverse) uses the server's order where it has one; otherwise the screen reads every matching record and sorts them locally, so the order is right across pages. `Enter` opens the record, `.` opens the row menu, `n` creates, `e` edits, `j` shows the record as JSON (`y` copies it), `y` in the grid copies the record's id, and `Del` deletes after the dashboard's confirmation (a typed word where the dashboard asks for one). When rows are marked with `Space`, `Del` deletes all of them. Screens whose dashboard page updates live (Deployments and Incidents) refresh when the server sends `deployment.changed` or `incident.changed`, without moving the cursor. People without the role to change a list see the dashboard's read-only hint and no create, edit, or delete actions; Configuration items follow the dashboard's scoping rules, so a regular user can edit only their own personal items.

Create and edit forms open as dialogs with the dashboard's fields and labels. `Tab` and `Shift+Tab` move between fields, `Enter` or `Space` opens a picker or toggles a checkbox, and `Ctrl+S` saves. Required fields are checked before anything is sent, and a server error stays in the dialog under the form so nothing typed is lost. `Esc` cancels; when the form has unsaved changes the first `Esc` warns and the second discards. Long text fields (summaries, notes, Markdown content, prompt bodies) edit in place with word wrap, undo (`Ctrl+Z`, `Ctrl+Y`), and a character count, and `Ctrl+E` opens the text in `$VISUAL` or `$EDITOR`; the TUI suspends while the editor runs and takes the saved text back. List fields such as verification definitions, runbook steps, and pipeline stages use `a` to add, `Enter` to edit, `Del` to remove, and `Alt+Up` / `Alt+Down` to reorder.

A detail page shows the record's name and status badges, a row of action buttons, and the dashboard's panels as tabs: `[` and `]` switch panels (inside a text field, where those keys type, use `Ctrl+PgUp` / `Ctrl+PgDn` or `Alt+1` to `Alt+9`), `Tab` moves between the buttons and the panel (on panels that are editors, focus starts on the buttons so single-key actions work; `Tab` into the fields to type, and `Ctrl+S` saves from anywhere on the page), and every action is also in the Actions menu (`F10`) and the palette, some with a key of their own (`e` Edit, `j` View JSON, `Del` Delete). Rows drawn as links open the related record with `Enter`. Actions that hand work to another screen carry their context the way the dashboard does: Run Check opens the Checks tab with the Run Check form filled in, Create Incident opens a prefilled new incident, Deploy opens a prefilled new deployment, and Runbook carries the execution context to the runbook you open.

## Operations

The OPERATIONS screens are the dashboard's Home, Needs You, Planning, Dispatch, Backlog, Fleet Actions, Missions, Voyages, Merge Queue, and Jobs pages. They share one shape, so what you learn on one list works on all of them.

Every list has a heading and subtitle, a toolbar, the filter row, and the shared grid. `/` jumps into the filters, `Tab` moves between them, and `Esc` or `Enter` returns to the list. Selects filter on the server (status, user scope); text filters narrow the loaded page as you type, exactly like the dashboard's column filters. `Enter` opens the selected row, `.` opens its action menu with the same items as the dashboard's row menu, and the common actions also have single keys, shown in the menu and the help overlay: `n` new, `j` View JSON, `y` copy the id, `d` diff, `l` log, `r` restart, `t` transition, `x` cancel, and `Del` for the permanent delete or purge. `Space` marks rows; bulk actions such as Delete Selected appear in the toolbar with the count once something is marked. Every action is also in the Actions menu (`F10`) and the palette (`Ctrl+K`), where row actions read "Selected row: ...". Lists refresh on the auto-refresh interval (15 seconds unless you pick another in View), on `F5`, and when a related socket event arrives, and a refresh never moves your cursor or clears your marks.

Detail screens show the record's title and status, a subtitle, the header buttons the dashboard shows, and the record's panels as tabs (`[` and `]`, or `Alt+1` to `Alt+9`). `.` opens the full action menu, the dashboard's More menu included. Forms open as dialogs: `Tab` moves between fields, `Enter` or `Space` opens a select, multi-line fields take `Enter` for a new line and `Ctrl+E` for `$EDITOR`, `Ctrl+S` submits, and `Esc` cancels. Validation messages appear under the field, and server errors appear above the buttons or in the error dialog with the request id.

Logs open in the log viewer: `+` and `-` step through 100, 200, 500, and 1000 lines, `f` follows (refreshing every second until the mission finishes, then one last refresh), `r` toggles readable formatting, `/` searches, and `y` copies. Diffs open in the diff viewer, where `]` and `[` jump between files.

### Home

Home (`g h`) is the dashboard's System Status page as one scrolling page. `Tab` moves from section to section and the page scrolls to keep the focused one in view; `PgUp`, `PgDn`, and the mouse wheel scroll freely. The header has Setup Wizard (`w`), Dispatch (`D`), and New Voyage (`V`), and the Ask band below it has Ask Armada (`a`), Needs You (`i`), Dispatch, and Diagnostics (`G`). Alert banners appear for stalled captains, failed missions, failed landings, pending work while captains sit idle, and pending work with no captains, each with the dashboard's wording and a View link where the dashboard has one. The KPI tiles (captains idle, working, and stalled; active voyages with memory-pressure deferrals; missions by status; active fleet action runs, running and pending) open their screens with `Enter`. Tenant admins also get Import repositories (`I`) and Run fleet action (`F`), and the vessel health tiles open the Health tab with the dashboard's filters. Mission History is a stacked bar chart drawn in text, `#` for complete, `x` for failed, and `.` for other, with the fleet, vessel, and range (last hour, day, week, month) filters and the totals above it. Voyage Progress lists active voyages with a progress bar (`j` shows the JSON). Recent Missions filters by status, vessel, and captain and offers View Detail, View JSON, Restart (for failed, cancelled, and failed-landing missions), and Delete; `M` goes to the full list. Recent Signals closes the page. Home reloads when any socket message arrives (at most every two seconds), polls every 30 seconds as the dashboard does, and also follows the auto-refresh interval.

### Needs You

Needs You (`g i`) shows the totals (Total, Critical, Warning, Unread alerts), the inbox items with their severity, title, and detail (`Enter` opens the item), and Recent alerts, the latest eight unread notifications (`Enter` marks one read and opens it, `m` marks all read). When nothing is waiting it says "You are all caught up." The same inbox feeds the Approvals center and the sidebar badge.

### Jobs

Jobs (`g j`) lists background jobs with their name (and error reason), kind, status, progress, and created and updated times, newest first. `x` cancels a job that has not finished, `j` shows its JSON, and the list refreshes on the auto-refresh interval.

### Planning

Planning (`/planning`) has four panels, switched with `[` and `]` or `Alt+1` to `Alt+4`: Start Session, Recent Sessions, Current Session, and Dispatch From Session. Start Session takes a title, an idle captain on a supported runtime (busy or unsupported captains are listed but cannot be chosen), an optional fleet filter, a vessel, a pipeline or "Inherit later during dispatch", and playbooks; `Ctrl+S` starts it. A handoff from a backlog item, an incident, the Setup Wizard, the Workspace, or a captain fills the form and shows the dashboard's banner, and a carried prompt lands in the new session's composer. The compact Vessel Readiness panel follows the chosen vessel, and `Alt+R` opens the full panel. Recent Sessions lists title, captain, vessel, pipeline, status, and update time; `Enter` opens a session, `E` ends it after a confirmation, `Del` deletes it, and `X` deletes all of them after you type "delete". Current Session shows the captain, runtime, vessel, branch, pipeline, playbook count, update time, and message count above the transcript. Replies render as Markdown with tool chips, collapsible thinking (`t`), and a metrics line, and they update live as the captain streams; the waiting text rotates every four seconds. `Enter` sends, `Ctrl+J` adds a line, `Ctrl+E` opens `$EDITOR`, `Ctrl+C` stops the turn, and `Alt+S` and `Alt+T` toggle streaming and show-thinking. In the transcript, `Enter` makes a reply the dispatch draft, `o` opens it in Dispatch, `x` shows its tool calls, and `y` copies it. Dispatch From Session holds the voyage title and mission description seeded from the selected reply, with Summarize Draft (`u`), Open In Dispatch (`O`), and Dispatch (`D` or `Ctrl+S`). Opening in Dispatch first releases the session's captain and dock, as the dashboard does.

### Dispatch and the Backlog

Dispatch sends a described task to a vessel as a voyage. Choose the vessel, a pipeline or inherit, a priority (default 100), an optional voyage title, the description (`Ctrl+E` for `$EDITOR`), and playbooks; `Enter` on the playbooks field manages them (`a` adds, `m` changes the delivery mode, `Del` removes). Captain Assignments lists each step of the chosen pipeline with a preferred captain (seeded from the persona default) and a fallback tier (Auto, Economy, Standard, Premium); an inherited pipeline gets one "All steps" row. Arriving from Planning, the Workspace, an incident, or a backlog item pre-fills the form and the dashboard's banner says where it came from; `Alt+B` opens the backlog item. Vessel Readiness appears once a vessel is chosen (`Alt+R` for details). `Ctrl+S` dispatches, shows the dashboard's toast, clears the title and description, and opens the voyage.

The Backlog tab of Dispatch (also at `/objectives`) shows four counts (backlog items, ready for planning, ready for dispatch, blocked) and the group pills, which `1` to `5` select. The filter row covers search, kind, priority, backlog state, effort, status, fleet, vessel, owner, target version, title, and the user for admins; the sort select orders by rank, priority, last updated, or due date, and `X` clears everything. Rows show rank, the item with owner, category, and version, its shape, its state with blockers, its scope, and due and updated times. Tenant administrators move an item with `Alt+Up` and `Alt+Down`, duplicate it (`u`), delete it after the dashboard's confirmation (`Del`), import a GitHub issue or pull request (`i`), and create an item (`n`).

A backlog item opens on its edit form with every field the dashboard edits; tags are one `key:value` per line, long fields open in `$EDITOR` with `Ctrl+E`, `Ctrl+S` saves, and Back (`b` or `Esc`) asks before throwing away changes. Overview shows the summary cards and the GitHub source, and Links lists every linked fleet, vessel, planning session, voyage, mission, check, release, deployment, and incident (`Enter` opens one). The actions are View JSON, History (`H`), Refresh GitHub (`F`), Start Planning (`P`), Open In Dispatch (`D`), Draft Release (`R`), Duplicate, and Delete; Start Planning and Open In Dispatch carry the dashboard's prompts. Refinement starts a captain-backed session (captain, vessel and fleet context, title, first prompt) and lists earlier sessions. Transcript follows the selected session live; `Up` and `Down` pick a message, `Ctrl+S` sends, `m` summarizes, `A` applies the summary to the item, `x` stops the session, and `X` deletes it. Summary Draft shows the latest summary and its method. A socket update refills the form only when it has no unsaved changes.

### Fleet Actions

The Actions tab lists saved actions with kind, source (built-in or custom), timeout, concurrency, and created and updated times. Tenant admins press `n` for a new action, `e` to edit, `u` to duplicate, `r` to run the selected action, `R` to run any action, and `Del` to delete; deleting a built-in hides it, and the confirmation says so. The form follows the dashboard: Command actions take command text, a timeout of 5 to 7200 seconds, and the clean-tree check; Mission actions take a prompt template, pipeline, and persona; concurrency is 1 to 32; unknown template variables are rejected; Template variables inserts one at the cursor; and `Ctrl+E` edits the body in `$EDITOR`.

Running an action opens a vessel picker that filters by name or path and by fleet; `Space` toggles a vessel, `Ctrl+A` selects every visible one, and `Ctrl+S` continues (at most 500 vessels). The run dialog offers the saved action (with the skip-dirty override) or an ad hoc definition, sets concurrency, and previews the rendered text for the first vessel; `Ctrl+S` moves to the review step, `Esc` goes back, and Run on N vessels starts the run and opens its page.

The Runs tab lists runs with a status filter, a progress bar and summary, created (sortable), started, completed, and duration; `Enter` opens a run and `x` cancels an active one after the confirmation. A run's page shows the progress bar (`#` succeeded, `x` failed, `-` skipped, `/` cancelled, `.` remaining) and counts, timing, the timeout and clean-tree check, the command or prompt snapshot, and the targets table with its status filter (`F`). While the run is active the page refreshes every five seconds, pausing while a drawer or dialog is open. `R` re-runs failed targets and `x` cancels the run. `Enter` on a Command target opens a drawer with status, reason, exit code, timing, the rendered command (`y` copies it), and the tail of stdout and stderr (`o` and `e` open the full streams); Mission targets open their voyage.

### Missions, Voyages, and the Merge Queue

The Missions tab pages on the server and filters by status and, for admins, by user; the title, status, and branch filters narrow the page. Title, status, and priority sort. `n` opens Create Mission (title, description, vessel, mode, priority), `Space` marks rows for Delete Selected (`D`, a purge per mission), and the row menu has View Detail, Edit, Restart (`r`), Retry Landing (`L`, for missions that produced work or failed to land), View Diff (`d`), View Log (`l`), Transition Status (`t`), View JSON (`j`), the vessel, captain, and voyage links, Cancel (`x`), and Purge (`Del`).

The screen reloads on `mission.changed`.

Create Voyage (`/voyages/create`, or `V` on Home) takes the title, description, vessel, pipeline, the three auto flags, playbooks, and the missions (`Ctrl+N` adds one, `Ctrl+D` removes the focused one).

The Merge Queue tab filters by branch, target, status, vessel, and user, and sorts by branch, target, status, and priority. Process All (`P`) confirms first, Enqueue (`n`) takes branch, target, mission id, vessel, test command, and priority, and Delete Selected (`D`) removes the marked entries. The row menu has View Detail, Process (`p`), Cancel (`x`), Mission Diff (`d`) and Mission Log (`l`) when the entry has a mission, links, copy actions, View JSON, and Delete. An entry's page shows the Landing Preview for its branch, every field, and the test output in the log viewer.

History from a backlog item opens `/history?objectiveId=`.

## Build

The BUILD screens are the dashboard's Vessels hub (Vessels, Health, Fleets, and Workspace tabs, `g v`), the import wizard, the vessel page and onboarding, and the Captains hub (Captains and Docks tabs, `g c`). They use the same list and detail conventions as the Operations screens: `/` for the filters, `.` for the row menu, `Space` to mark rows, `j` for View JSON, `y` to copy the id, and `Del` to delete after the dashboard's confirmation.

### Vessels

The Vessels tab lists every repository with its fleet, repository URL, default branch, landing mode with its short explanation (for example `PullRequest (opens a PR)`), sync state against the remote (`in sync`, `2 ahead`, `1 behind`), and branch count; the sync and branch columns fill in from the server in the background. Administrators get a user filter; everyone filters by name, fleet, repository, and landing mode, and sorts by name, fleet, repository, default branch, and created. `n` opens the vessel form, `I` the import wizard (tenant admins), and marking rows shows a bar with Run action (`A`, the fleet action run dialog with the marked vessels), Delete Selected (`D`), and Clear selection. The row menu has Manage Branches (`b`), Manage Objectives (`O`, the Backlog filtered to the vessel), Manage Fleet (`f`), Open Workspace (`w`), View Detail (`o` or `Enter`), Build Context or Refine Context (`B`), Edit (`e`), Duplicate (`u`, which opens the copy's edit form), View JSON, Copy ID, Copy URL (`Y`), and Delete.

The vessel form holds every field of both dashboard vessel forms in one dialog: name, fleet, repository URL, default branch, local path, working directory, the GitHub token override (masked; leave it blank to keep a stored token, or tick Clear to remove it), landing mode with its full explanation, branch cleanup, agent auto-approve, default pipeline, concurrent missions, model context, the release and hotfix prefixes, protected branch patterns, the three branch policy switches, the dock boundary (secret scan, protected paths, identifier denylist), the auto-land gate (maximum files and lines, allowed and denied paths), the in-dock Definition-of-Done gate (build and test commands, per-phase timeout of 30 to 7200 seconds), and the project context, style guide, and model context. List fields take one entry per line, and the long fields open in `$EDITOR` with `Ctrl+E`. Edits send the whole record, so nothing the form leaves out is cleared.

Manage Branches lists each branch with its default and current tags, commits ahead and behind, and last commit. `p` pushes the selected branch, `y` copies its name, `r` refreshes, and the Merge a branch row below takes a source, a target, and Push after merge (`m` or the Merge button merges; the dashboard's warnings appear when either branch is missing or they are the same). Build Context asks for a captain (the first is preselected) and optional focus notes, then waits while the captain writes or refines the vessel's Model Context.

### Importing repositories

`/vessels/import` (or `I` on the Vessels tab) onboards existing local repositories in bulk. On the Source step, pick Paste paths (one folder per line; quotes are stripped and duplicates dropped) or Browse, which walks the Admiral host's allowed import roots: `Enter` or `Right` expands a folder, `Space` selects it, git repositories and worktrees are tagged, and worktrees can be selected only after Allow selecting worktrees. Max depth takes 1 to 16 or stays empty for the server default. `Ctrl+S` starts discovery, which runs as a background job; the wizard says so, polls every two seconds, and can be left at any time (`h` opens the import history, `s` starts over). The Review step shows the discovery hints, the status chips (`f` cycles the filter), a text filter (`/`), and the candidates: new repositories are selected, `Space` toggles an importable one, `Ctrl+A` toggles every importable candidate in view, `a` selects all new ones, and `C` clears. `]` switches to the defaults (fleet, default pipeline, landing mode) and the fleet recommendations: tick Recommend fleets with a captain, choose an idle captain (busy ones are listed but cannot be chosen), edit the instructions (Reset to default restores them), and decide whether the recommendations apply automatically. `Ctrl+S` imports the selection. Results shows the progress while the import runs in the background, the created, skipped, failed, and candidate counts, and each item's outcome and reason (`f` filters by outcome, `Enter` opens the vessel). When fleet recommendations were requested, `]` shows them: while the captain works you can stop it (`x`); when it failed you can retry (`R`); when it finished you can rename a fleet (`r`), edit its description (`e`), move a repository to another fleet (`m`), add a fleet (`a`), remove an empty one (`Del`), and apply them all (`A`, after the confirmation). Applied fleets can be edited and applied again (`E`). The import history lists every batch with its counts and a status filter; `Enter` continues a review or opens the results, and `?batch=ID` opens a batch directly. Leaving a review with `Esc` asks first, because the discovered batch is kept for later. If fleet recommendations are ticked without a captain, or the chosen captain no longer exists, the import is refused with a message that says which.

### Vessel Health

The Health tab (`/vessels/health`) grades every vessel. The summary chips count Fail, Warn, Pass, Unknown, Not applicable, and Not evaluated vessels; `1` to `6` filter to one of them and again to clear it. Beside them are the vessel count and the evaluation progress (or when the last one finished). Tenant administrators run Evaluate all (`E`), Re-evaluate selected (`R`), and Run action (`A`) for marked rows. The filters cover the name, fleet, the overall, dependency, and test statuses (each a multi-select), dirty, CI, divergence, the branch count range, and the last commit range; `X` clears them. Sorting and paging run on the server across all 17 sortable columns, and the filters, sort, and page are written back into the route query just as the dashboard writes them into its URL, so Back, Forward, and links such as `/vessels/health?overall=Fail&sort=VulnerableCount&dir=desc` restore the exact view. The column chooser (`c`) keeps Vessel and Overall pinned; Last commit and Evaluated start hidden.

`Enter` (or View details) opens the health inspector. Its sections switch with `[` and `]` or `1` to `5`: Summary (every measured value, including divergence against the default branch and upstream), Findings (one sentence per criterion, such as "Behind by 5 commits (ahead 2)."), Dependencies (ecosystem, project, package, version drift, vulnerability, and advisory, which `Enter` opens), Overrides, and Raw JSON. Tenant administrators override a criterion or Overall from Findings (`Enter`) or Overrides (`e` edits, `Del` removes after the confirmation, `Ctrl+S` saves the form with an optional note), and re-evaluate the vessel with `e`. `o` opens the vessel and `b` its branches.

### The vessel page and onboarding

A vessel's page (`/vessels/ID`) has Manage Objectives (`O`), Manage Fleet (`f`), Onboarding (`g`), Run Check (`k`, which opens the Checks tab's Run Check form for the default branch), Open Workspace (`w`), and Health (`h`, the same inspector) as buttons, and Edit (`e`), Duplicate, View JSON (`j`), and Delete in the action menu (`.`). The Overview panel shows the readiness report, the landing preview for the default branch, and every field; Context shows the project context, style guide, protected branches, dock boundary, and model context; Missions lists the vessel's missions. Onboarding (`/vessels/ID/onboarding`) counts completed steps, blocking issues, warnings, and environments, names the next recommended step (`n` follows its action), and lists the readiness report, the setup checklist grouped into Repository Basics, Workflow Profile, and Delivery Readiness, and the open issues. Its Steps panel lists every unfinished step that has an action; `Enter` follows it.

### Fleets

The Fleets tab lists fleets with their description, vessel count, active state, and created time, filters by name and description, and sorts by name, description, vessels, and created. `n` creates a fleet (name, description, default pipeline), `e` edits, `u` duplicates, and Delete Selected (`D`) removes the marked ones. A fleet's page (`/fleets/ID`) shows its fields and, on the Vessels panel, its vessels with their repository URL and branch (`Enter` opens one, `y` copies the URL).

### Workspace

The Workspace tab of the Vessels hub lists vessels, recent ones first, with their workspace state, branch, active missions, and sync; `Enter` opens a vessel's Workspace (`/workspace/ID`). The Workspace shows the branch, whether the working tree is dirty, the active missions, and the commits ahead and behind, a one-line readiness summary (`r` for the full report), the file tree on the left, and the editor on the right. `Tab` moves between them. In the tree, `Enter` opens a file or expands a folder (folders load as you open them), `Left` collapses or moves to the parent, and `Space` marks files for Plan, Dispatch, and context curation; marked files and any active mission that already touches them are listed under the tree. `n` creates a file (it opens as an unsaved tab and is written on the first save), `N` creates a folder, `R` renames or moves, `Del` deletes after the confirmation, and `i` shows the entry's metadata. Open files get tabs (an unsaved one is marked `*`; `Ctrl+PgUp` and `Ctrl+PgDn` switch, `Ctrl+W` closes), `Ctrl+S` saves with the content hash so a change made elsewhere since you opened the file is refused instead of overwritten, and `Ctrl+E` edits the file in `$EDITOR`. Binary, too-large, and read-only files show a highlighted, line-numbered preview instead of the editor. `k` runs a check, `P` opens Planning and `D` opens Dispatch with the marked files (or the open file) as a "Touch only ..." draft carried in the route query, `C` opens Vessel Context, where Append Selection adds the marked files to the project context, style guide, or model context before you save, `d` reviews the working tree's diff against HEAD in the diff viewer, `t` opens the terminal (one command at a time in the working tree; `Up` recalls earlier commands, `Ctrl+L` clears, and the output stays for the next time), `F` searches the files and opens a match, and `V` switches to another vessel. Expanded folders, recent files, and recent vessels are remembered in `tui.json`.

### Captains and Docks

The Captains tab (`g c`) lists captains with their tier, runtime, state (quarantined captains say until when), current mission, heartbeat, and created time, filtered by name, runtime, and state (and by user for administrators). `n` opens the captain form: name, runtime, model, the inference endpoint for API Endpoint captains, reasoning effort, capability tier, the auto-approve switch for CLI runtimes, system instructions, and, for Mux captains, the config directory, the endpoint (discovered endpoints are listed and can be chosen, and Refresh Mux Endpoints reloads them), base URL, adapter type, temperature, maximum tokens, system prompt path, and approval policy. The row menu has View Detail, Start Planning (`P`, for idle captains that support planning), Edit, Duplicate, View Tools (`t`, the MCP servers, runtime sources, internal tools, and MCP tools with their reachability), View JSON, View Notifications, Stop (`x`), Recall (`R`), Restart (`r`), and Delete, each with the dashboard's confirmation; Stop All (`X`) stops every captain after asking. A captain's page shows every field, the Mux endpoint settings, the quarantine with Lift Quarantine (`q`), and the current mission, with Recent Missions on the second panel. View Log (`l`) opens the captain log at 500 lines with the server's readable formatting (tool calls named, secrets redacted, noise dropped); `r` switches between readable and raw, and the usual log keys apply. The page's Edit form adds the allowed personas (a JSON array) and the preferred persona.

The Docks tab lists the git worktrees provisioned for captains with their vessel, captain, branch, worktree path, active state, and created time, filtered by branch and worktree path. Deleting a dock also cleans up its worktree. A dock's page (`/docks/ID`) shows every field and, when the dock recorded them, its starting point: the start commit, target and working branches, recent commits on the relevant paths, and the subject terms already in the tree.

## Delivery

Deployments. The Deployments tab (`g d`, or `/delivery?tab=deployments`) shows total, pending approval, running, succeeded, and failed or verification failed deployments, filters by search, status, verification state, and vessel on the server, and refreshes live on `deployment.changed`. `n` opens Create Deployment: choosing an environment fills in its name and vessel, choosing a release fills in an empty vessel, and the vessel narrows both pickers. A deployment's page (`/deployments/ID`, or `/deployments/new` to create one) has Approve (`a`) and Deny (`r`) while it waits for approval and Verify and Rollback afterwards, each confirmed with the dashboard's wording, plus Open Workspace, Run Check, Sync GitHub Actions, Runbook, Create Incident, Open Release, Edit (`e`), View JSON (`j`), and Delete. Its panels are Overview (status, verification, approval, monitoring window, regression alerts, the deployment's fields, the monitoring summary, and identifiers with links), Linked Checks, Runbook Executions, and Request Summary with a bar chart of the request buckets.

Environments. Delivery, Environments (`g d`, then `]` to the Environments tab, or `/delivery?tab=environments`) lists deployment targets with an overview line (total, active, default targets, require approval) and filters for search, kind, vessel, and active state. The filters run on the server and can be deep linked, for example `/delivery?tab=environments&kind=Production`. Press `n` to create an environment, `e` to edit, `.` for the row menu (Open, Edit, Duplicate, View JSON, Copy ID, Delete), and `Enter` to open it. The detail screen has Deploy, Run Check, Create Incident, and Runbook actions, which open those screens already filled in from this environment, along with Open Workspace, View JSON, Duplicate, and Delete. The Overview panel shows every field. Tenant administrators also get an Environment panel that edits every field, including the rollout monitoring window and interval, regression alerts, and the reusable verification definitions: `a` adds a definition, `Enter` edits it in a dialog, `Space` toggles it active, `Del` removes it, and `Alt+Up`/`Alt+Down` reorder. `Ctrl+S` saves. `/environments/new` opens the same editor for a new environment.

Releases. The Releases tab (`/delivery?tab=releases`) shows total, shipped, candidate, and failed or rolled back counts, filters by search, status, and vessel, and lists each release's linked work and publish time. `n` and `e` open the release form, where voyage, mission, and check run IDs are entered one per line or comma separated. A release's detail screen has Deploy and Run Check actions (prefilled), View JSON, Refresh Derived Fields, and Delete. Its panels are Overview, Release (the editor, saved with `Ctrl+S`), Linked Work (each voyage, mission, and check opens with `Enter`), Linked Backlog Items (`.` offers View History), Deployment Evidence, Artifacts, and GitHub Pull Requests (`Enter` opens the pull request in your browser). `/releases/new` creates a release; when a backlog item or check run hands one off, the form arrives prefilled and the new release is linked back to those backlog items.

Incidents. Open Delivery and switch to the Incidents tab (`g d`, then `]` or `Alt+4`), or deep link `/delivery?tab=incidents&status=Open&severity=Critical`. The overview line counts total, open, monitoring, mitigated, and closed or rolled back incidents. The search, status, and severity filters are applied by the server, and the list refreshes on its own whenever an incident changes. `Enter` opens an incident, `.` shows Open, View JSON, Copy ID, and Delete, and tenant admins press `n` for Create Incident. Other screens hand off a prefilled incident by opening `/incidents/new`, which shows the full form. The incident page lists every field, the linked deployment, environment, and release (press `Enter` on a link row to follow it), and the runbook executions. Its actions are Plan Hotfix, Dispatch Hotfix, Runbook (starts a runbook execution with the hotfix prompt filled in), Rollback Deployment (asks first, then records the rollback on the incident), Open Deployment, Open Environment, View JSON (`j`), Edit (`e`), and Delete (`Del`).

Checks. The Checks tab (`/delivery?tab=checks`) counts total, passed, failed, and running check runs. It filters by vessel, status, source (Armada or External), and check type on the server. Each row shows how the run compares with the previous comparable run (same vessel and type, preferring the same branch, profile, or environment), marked when it regressed or improved. `n` opens Run Check: pick a vessel and the dialog shows the resolved workflow profile, its commands, and a preflight readiness report. The check types narrow to what the profile can run, and preflight errors block the run. When a deployment, environment, runbook, or release screen asks you to run a check, the dialog opens on this tab already filled in. A check run page (`/checks/:id`) has panels for the overview, the comparison with every delta, test results and coverage, artifacts, and the output log (follow with `f`, search with `/`, copy with `y`). Its actions are Retry (`r`), Draft Release (opens a new release prefilled with the run, its mission, and its voyage), View JSON (`j`), and Delete (`Del`, confirmed).

The Runbooks tab (Delivery, `g d` then `]` until Runbooks, or `/delivery?tab=runbooks`) lists runbooks with their binding to a workflow profile, environment and default check, their step and parameter counts, and their executions. The overview line counts runbooks, active runbooks, executions and running executions. Type `/` to search, or pick All states, Active or Inactive; both filters run on the server. `n` creates a runbook, and `.` opens the row menu with Open, Duplicate, View JSON, a "Running: N" shortcut when executions are running, and Delete for runbooks you may edit. When a deployment or incident hands off a runbook execution, the tab says so, and the runbook you open next starts its execution with those defaults.

A runbook (`/runbooks/ID`, or `/runbooks/ID?executionId=EXEC` to open one execution) has four panels: Overview, Runbook, Executions and Execution Progress. The Runbook panel edits the definition in place: overview Markdown in the field or in your editor with `Ctrl+E`, and parameters and steps with `a` to add, `Enter` to edit, `Del` to remove and `Alt+Up`/`Alt+Down` to reorder. `Ctrl+S` saves. `x` starts an execution. On Execution Progress, `Space` ticks a step, `Enter` edits its note, and `Ctrl+S` saves progress. Mark Completed and Cancel Execution ask for confirmation, and Run Check opens the Checks tab's Run Check form prefilled for the runbook's environment.

## Configuration

Workflow Profiles. Configuration, Workflow Profiles (`g o`, then `]` to the tab, or `/configuration?tab=workflow-profiles`) lists the command profiles that tell Armada how a project builds, tests, packages, releases, deploys, and verifies itself. The overview line counts profiles, active profiles, defaults, and environment targets. The search, scope (Global, Fleet, Vessel), and status filters are applied on the server and can be deep linked, for example `?scope=Fleet&status=active`. `n` opens the quick form for the core details, `Enter` opens a profile, and `.` offers Open, Edit, Duplicate, View JSON, Copy ID, and Delete. Anyone can create a profile; profiles made by non-administrators are personal, and only a profile's owner or a tenant administrator can edit or delete it.

The profile screen (`/workflow-profiles/ID`, or `/workflow-profiles/new` to create one) is a full editor. The Profile panel holds the name, scope, fleet or vessel, defaults, language hints, expected artifacts, the required inputs (provider, environment scope, key or path, note), every command from lint through changelog generation, and the per-environment deploy, rollback, smoke test, health check, and verification commands. Long commands open in `$EDITOR` with `Ctrl+E`, and `Ctrl+S` saves. `v` validates the current values on the server and switches to the Validation panel, which lists errors, warnings, available check types, and the resolved commands. Preview for Vessel shows how the profile resolves for a vessel you pick. The panels are Profile, Validation, Vessel Preview, and Details.

Project Profiles. Configuration, Project Profiles (`/configuration?tab=project-profiles`) lists per-project customizations that bind a default pipeline, a workflow profile, persona prompt overrides, and skills, resolved global to fleet to vessel. The overview counts profiles, active profiles, defaults, and persona overrides, and the search, scope, and status filters work the same way as on Workflow Profiles. `n` creates a profile and `.` offers Open, Edit, View JSON, Copy ID, and Delete, subject to the same ownership rules. The project profile screen (`/project-profiles/ID`) edits the profile in place. Persona overrides are a list: `a` adds one (persona, prompt template, enabled, additional instructions), `Space` turns one on or off, and `Enter` edits it. Skills are one per line. On the Persona Prompt Diff panel, pick a persona and choose Preview (or press `p`) to compare the base prompt with the effective prompt as a diff, with removed lines marked `-` and added lines marked `+`.

Skills and Playbooks. Configuration, Skills (`g o`, then `]` to the Skills tab, or `/configuration?tab=skills`) lists reusable capability snippets with totals for active, inactive, and categories. The search box and category picker filter on the server. `n` creates a skill and `e` edits the selected one, in a form whose Content field edits inline or opens in `$EDITOR` with `Ctrl+E`. Anyone can create a personal skill, while editing and deleting follow the dashboard's scope rules: tenant-wide items belong to administrators, personal items to their owner. `Enter` opens `/skills/ID`, with Overview and Content panels. Playbooks (`/configuration?tab=playbooks`) work the same way for Markdown playbooks, add Duplicate to the row menu, and the detail page `/playbooks/ID` shows character, line, and heading counts beside a rendered preview.

Endpoints, Harbors, and Memory. Endpoints (`/configuration?tab=endpoints`) manages embedding and inference model endpoints. The Health column shows the latest status and a short history strip (`+` ok, `x` failed, `~` mixed). `h` opens the health detail with uptime, history span, consecutive results, the last error, and a chart, and `v` validates the endpoint against its model, there or from the list. Administrators run a health sweep with `H`. The endpoint form checks the provider rules before saving and never shows a stored secret; leave the key blank to keep it. Harbors (`/configuration?tab=harbors`) lists connected host runners; `Enter` shows details and capabilities, `t` enables or disables routing, and administrators register, edit, and delete harbors. Memory (`/configuration?tab=memory`) pages through durable memories on the server with type and search filters; `Enter` shows the JSON and `Del` deletes after confirmation, and as a TUI extension `n` and `e` create and edit memories.

Personas. Configuration, Personas (`g o`, then `]` to the Personas tab, or `/personas`) lists every persona with its prompt template, visibility, built-in and active flags, sorted by name. Type `/` to filter by name, description, or template; `s`/`S` sorts the focused column. `n` creates a persona (name, description, prompt template, and, for administrators, tenant-wide or personal scope), and `.` opens the row menu: View Detail, Edit, Duplicate, Edit Backing Prompt, View JSON, Copy ID, and Delete. Built-in personas cannot be deleted, and you can edit only what your role and the item's scope allow. `Enter` opens `/personas/NAME`. Its Overview panel shows the default captain and links to the prompt template. Its Backing Prompt panel edits the template's description and content in place; press `Ctrl+E` to edit the content in `$EDITOR`. Save Prompt, Reset to Default (with confirmation), and Open Full Template are in the action bar and the Actions menu. Edit (`e`) changes the description, template, and default captain.

Pipelines. Configuration, Pipelines (`/pipelines`) shows each pipeline's stage chain, for example `Worker -> Judge [review]`. The create and edit form keeps the stages in a list: `a` adds a stage, `Enter` edits one (persona, optional, review gate, and whether a denied review retries the stage or fails the pipeline), `Del` removes it, and `Alt+Up`/`Alt+Down` reorders. The detail screen, `/pipelines/NAME`, shows an Overview and a Flow panel with the chain and a stage table. `r` runs the pipeline: choose a vessel, a title, and an objective, and Launch Voyage opens the new voyage. Built-in pipelines cannot be deleted; deleting any other pipeline asks for confirmation.

Prompts. Configuration, Prompts (`/prompt-templates`) filters by category (mission, persona, structure, commit, landing, agent, import), name, and description; a link such as `/configuration?tab=prompts&category=persona` opens with the category set. `.` offers Edit or Open, Duplicate, View JSON, and Reset to Default for built-in templates. `n` opens `/prompt-templates/create`, which requires a name, category, and content. On a template page, the Template panel edits the description and content with a character count and an unsaved marker; `Ctrl+E` opens `$EDITOR` and `Ctrl+S` saves. `Ctrl+P`, or the Parameters panel, inserts a placeholder such as `{MissionId}` at the cursor, grouped by Mission, Vessel, Captain, Pipeline Context, and System. Reset to Default restores a built-in template after confirmation.

## Activity and System screens

The Activity hub (`g y`), Jobs (`g j`), the API Explorer (`g x`), and the Settings hub (`g s`) are built. Every screen uses the dashboard's wording, so the language picker translates them like the rest of the shell. Lists share the grid keys from the key map; screen actions also appear under Actions in the menu bar (`F10`) and in the command palette, so `Ctrl+K` then "Export CSV" or "Backup Now" runs the action on the current screen. ### Viewing activity

The All Activity tab is the unified timeline: backlog refinement, planning, dispatch, releases, deployments, incidents, API requests, and events in one list, newest first. The cards at the top count the visible entries, errors, warnings, and distinct source types, and a line under the filters breaks the entries down by source. Filter by free text, backlog item, actor, vessel, source type, or postmortem context, then press `Enter` in a text field or `a` (Apply) to reload; Reset clears every filter. `Enter` on an entry opens the record it points to, and the row menu (`.`) also offers View JSON for the entry's metadata, Open Workspace for its vessel, and Delete for entries that come from the API request log. Deep links such as `/activity?source=history&actor=alice&postmortemOnly=true` open with those filters applied.

Saved views remember a set of filters under a name. Press `w` to save the current filters and `v` to open the list, where you can apply or delete a view. Views are kept in `tui-activity-views.json` next to `tui.json`, so they follow your preferences file rather than a browser. Export JSON, Export CSV, and Export Markdown write up to 5,000 entries that match the current filters, with the same content as the dashboard's downloads, to a file named `armada-history-<timestamp>` by default.

The Token Usage tab charts model tokens over the last hour, day, week, or month (`h`, `d`, `w`, `m`). The cards show total, input, output, and cached tokens, and a note says how many records were estimated rather than reported. "Usage over time" stacks each model's tokens per time bucket, or with `t` splits them into input, output, and cached tokens. `b` switches between stacked bars and lines, and every series has its own glyph as well as its own color. "Usage by model" ranks models by total tokens. Where the dashboard copies a chart as an image, the TUI copies it as a tab-separated table (`y`), and `e` exports the time buckets with a column per model as CSV.

### API request history

The API Requests tab lists the API traffic the server has captured. Four cards show the total requests, success rate, failures, and average duration for the current window, and the Activity chart stacks successful and failed requests per time bucket; move to its range tabs with `Tab` and use `Left` and `Right` to choose Last Hour, Last Day, Last Week, or Last Month. Press `f` to show the filters: method, status code, route, principal, credential, result, from, and to. A global admin also gets a tenant filter, and global and tenant admins get a user filter. Text filters apply on `Enter`, pickers as soon as you choose, and Reset returns to the last 24 hours. Failed requests show a `!` before the status code.

`Enter` on a row opens the request detail drawer: entry ID, principal, auth method, status, duration, capture time, path and query parameters, request and response headers, and both bodies, noting when a stored body was truncated. In the drawer, `r` replays the request in the API Explorer, `Del` deletes the entry, `y` copies one block or everything, and `Esc` closes it. A link to `/requests/<id>` opens the drawer directly. To delete in bulk, mark rows with `Space` and press `Del`, or use Delete Visible Range, which reads Delete Filtered once other filters are set. Every delete asks for confirmation.

### Events, signals, and jobs

The Events tab is the system event log. It pages on the server, and the filter row narrows the current page by event type, entity type, and message as you type; admins also get a User picker. The row menu offers View Detail, View JSON, Delete, and links to the entity, captain, mission, vessel, and voyage. `Enter` opens the event's detail page, which pretty-prints a JSON payload; `Enter` on a linked field opens that record and `y` copies the field.

The Signals tab lists messages between the Admiral and captains. Filter by type, captain, unread only, and (for admins) user; Clear Filters resets them, and a second row searches type, sender, recipient, and payload on the current page. `Enter` opens a signal, `r` marks the selected one read, and `.` opens the row menu. To send a signal press `n`, choose the type, write the payload (`Ctrl+E` opens your editor), choose a captain or leave "Admiral (broadcast)", and press `Ctrl+S`. The detail page links the sender, recipient, and related mission and can mark the signal read or delete it.

Jobs lists background jobs with their kind, status, progress, and the error reason of failed jobs. `x` cancels the selected job while it is still queued or running. The list refreshes on the screen's auto-refresh interval and with `F5`.

### Using the API Explorer

The API Explorer reads the server's live OpenAPI document. Pick a category, type part of a path or summary into the filter, and choose an operation. The builder fills in path, query, and header parameters with their example or default values and, for operations that take a body, an example JSON body built from the schema; `Ctrl+E` edits the body in `$EDITOR`. The Request Preview line shows the exact URL that will be called. `F9` sends the request with your session's credentials and `F8` aborts it. The response pane shows the status, content type, duration, and size, with Preview, Body, Headers, and Code views; the Code view shows the request as curl, JavaScript fetch, or C#, and works before you send anything. `y` copies the current view, Save Response writes the body to a file, and OpenAPI JSON and Swagger open in your browser. Replay in API Explorer, from the request history, opens the matching operation with the captured path values, query values, headers, and body filled in, minus your stored session token.

### Changing settings

The Server tab of Settings shows the Admiral's health, uptime, connection (Live over the WebSocket or HTTP), and remote tunnel, then the server details and every settings section the dashboard has: Server Configuration, Rebuild Armada, Agent Settings, Planning Session Settings, Repository Health, Vessel Import, Fleet Actions, Data Retention, Remote Control, MCP Configuration, and System Paths. Move through the page with `Tab` and `Shift+Tab`; it scrolls to follow you. Each section saves on its own: press `Ctrl+S` anywhere in a section or use its Save button. Values are checked with the dashboard's messages and a section with an invalid value will not save. Vessel Import, Fleet Actions, and Data Retention save only after a change and offer Discard changes. The header says "Unsaved changes" while any section has edits, and a refresh never overwrites them. Lists such as allowed roots take one entry per line, and `Ctrl+E` opens them in your editor. Masked secrets in Remote Control are revealed with `Ctrl+R`, and turning on the tunnel asks for confirmation. Repository Health is editable only by a global admin; others see it read-only. MCP snippets and system paths copy with `Enter` or `y`. The Server page has no login rate limit or Ask settings, so the TUI has none either; they stay in `settings.json`.

Diagnostics runs the server's health checks when you open it and again with `r`. The header shows the verdict (Healthy, Warnings, or Unhealthy), the cards count passed, warning, and failed checks, and `Enter` on a check shows its full message.

### Backing up and restoring

Global admins see Database Backup on the Server tab. Backup Now downloads a backup ZIP and asks where to save it, suggesting the server's file name. Restore from Backup asks for a ZIP on this machine, asks you to confirm, uploads it, and reloads the page; restart the server afterward. Through Armada.Proxy, backup still works but restore is blocked.

### Restarting, stopping, and rebuilding

Server Actions, also for global admins, has Setup Wizard, Health Check, Restart Server, Stop Server, Factory Reset, Rebuild Armada, and Roll Back. Each server-changing action asks for confirmation with the dashboard's wording, and nothing is sent until you confirm. Factory reset deletes all data, including the database, logs, docks, and repositories, but keeps settings. Through Armada.Proxy these local-only actions are disabled and a banner says why.

To rebuild the Admiral from source, choose the vessel that holds Armada's source under Rebuild Armada and save. Rebuild Armada then offers the vessel's branches and a field for any branch, tag, or commit, with the default branch filled in. After you confirm, the build log opens and updates every second and a half until the build succeeds, fails, or the server begins cutting over to the new build. Close the log with `Esc`, reopen it with Build Log, and copy it with `y`. After a successful rebuild, Roll Back returns to the previous build.

### Managing tenants, users, and credentials

The Settings hub has Tenants, Users, and Credentials tabs. Global admins see every tenant and can create one with `n`, edit one with `Enter`, and delete with `Del`; other users see their own tenant read-only. A new tenant gets an `admin@armada` account. Type its password in Admin Password (optional), at least 8 characters, or leave it blank and the server generates one. A generated password is shown once in a dialog with the admin email: press `y` to copy it before closing, because it cannot be retrieved later and the TUI does not keep it. Users and Credentials are for tenant admins and global admins, with search fields and a tenant filter above the grid (Credentials also filters by user).

To add a user, press `n` and fill in the email, the optional first and last name, and the password twice. The tenant is chosen for you unless you are a global admin. Global admins can also grant Global Admin, and tenant admins can grant Tenant Admin. `Ctrl+S` saves. When you edit a user, leave the password fields blank to keep the current password. When you change your own password here, the form also asks for your Current Password and refuses to save without it; a wrong one shows "Current password is incorrect." Setting another user's password does not ask for it. The form refuses to save without an email, without a password on a new user, or when the two passwords differ.

A credential is an API bearer token for a user. Press `n`, pick the user (global admins also pick the tenant), give it an optional name, and save. The new token is shown once: press `y` to copy it before closing, because the list shows it masked afterward. Edit a credential to rename it or turn it off.

Every list supports `Space` to select rows, `Ctrl+A` to select the page, and `Del` to delete the selection. Deleting tenants, users, or credentials asks you to type `delete` to confirm, as the dashboard does. Through Armada.Proxy, create, edit, and delete are hidden and a banner explains why.

### Running the setup wizard

The setup wizard gets a new Armada ready to dispatch one safe first mission. It opens on its own after you sign in when the server has no fleets, vessels, or captains, or when one of them is still missing and you have not finished or skipped setup before. A start route given with `--route` wins for that sign-in. You can open it at any time from Server Actions on the Settings Server tab or with `--route /setup`.

The wizard has six steps, shown across the top with the current one in brackets and finished ones marked `[x]`. Objective explains what will happen; `Tab` to the buttons and choose Start Setup. Fleet, Vessel, and Captain each let you reuse an existing record (Use Existing) or create a new one (Create New); only idle captains are offered. Fill in the form with `Tab` and `Shift+Tab`, open pickers with `Enter`, and press `Ctrl+S` to save the step and move on. Long text fields open in your editor with `Ctrl+E`. For a Mux captain the wizard lists your saved Mux endpoints.

Dispatch sends a read-only onboarding mission to the vessel you chose; the defaults ask the captain to inspect the repository and report a summary without changing files. Handoff follows the mission until it settles, shows the vessel's readiness and the next recommended step, and offers links into Vessel Onboarding, Backlog, Planning, Workspace, Workflow Profiles, Environments, Checks, and Playbooks. Skip Setup and Finish Setup both mark setup as done in your TUI preferences (`SetupCompleted` in `tui.json`) and take you to Missions. Back returns to an earlier step and keeps what you typed.

## Themes, icons, and display

View offers Dark, Light, High contrast, and Auto. Auto reads the terminal background from `COLORFGBG` and picks Dark when it cannot tell; when `NO_COLOR` is set it picks High contrast. High contrast uses black and white with bright accents, ASCII borders, and reverse video or underline for every selected or focused item, so it also reads on a terminal without color.

View also offers Icons: Auto, Unicode, and ASCII (saved as `Glyphs` in `tui.json`). ASCII draws borders with `+`, `-`, and `|` and writes an ASCII equivalent for every box-drawing, block, Braille, arrow, and bullet character a widget uses (charts switch to `#`, `=`, `+`, and similar), so nothing depends on the terminal's Unicode font. Text you or the server wrote (names, CJK, accented letters) is never changed. Auto picks ASCII when the terminal is not UTF-8: `TERM=dumb`, a `LC_ALL`, `LC_CTYPE`, or `LANG` value that does not name UTF-8 (such as `C` or `POSIX`), or legacy conhost on Windows (Windows Terminal, ConEmu, and terminals that set `TERM_PROGRAM` count as UTF-8). If borders look broken over SSH or in an old console, choose Icons: ASCII.

The sidebar, the main screen, and the Ask dock each sit inside a one-cell border, so you can always see where keyboard focus is. The pane that has focus draws its border in the theme's focus color with heavy lines (`+`, `-`, and `|` in ASCII icon mode); the other panes draw a dim, light line. When focus is inside part of a screen (a grid, the filter row, a hub's tab strip, a detail panel, the Ask thread list, transcript, or composer, the workspace tree or editor), only the stretch of the main border alongside that part lights up: for example the right edge beside the composer, or the left and right edges beside a list. If the focused part touches no edge of the main area, the whole border lights. Tab, Shift+Tab, `Ctrl+J`, and Esc in Ask all move the lit border with the focus, and the per-widget highlight (the grid cursor, the focused field, the active tab) is unchanged. The border cells are reserved whether or not a pane has focus, so nothing moves when focus does. In High contrast the focused border is reverse video, so it does not depend on color. At the 80x24 minimum every pane still has its full border; a pane under three rows or columns (not possible in the built-in layout) falls back to a one-column bar on its left edge while it has focus.

No state is shown by color alone. Statuses carry a symbol and their name (`+ Complete`, `x Failed`, `! Stalled`, `~ InProgress`, `- other`), the active tab is in brackets, the current sidebar item has `>`, completed wizard steps have `+`, and the header spells out `Live`, `Offline`, `Healthy`, and `Unreachable`.

At the 80x24 minimum the sidebar is hidden (`Ctrl+B` shows it over the screen), between 90 and 109 columns it shows icons, and from 110 columns it is full. The status bar always keeps `? Help` visible, and the header gives approvals and the bell priority over your user and tenant name. Tables give their title or name column room first; ID columns shrink with the middle cut out (`msn_0...WXYZ4`) and are the first columns dropped when a table is narrow, so open a row or press `y` to copy a full ID.

The language picker uses the dashboard's catalog (served at `/dashboard/i18n/armada.json`) and the same nine languages, including Simplified and Traditional Chinese, Cantonese, and Japanese; widths are measured in terminal cells, so CJK text lines up.

## Performance

The TUI composes a frame only when something changed (a key, mouse, or paste; data arriving; a resize) and otherwise a few times a second for clocks and relative times, so an idle TUI uses about 1 percent of one core. Tables draw only the rows on screen and page on the server where the API pages; a 10,000-row table renders a frame in about 1 ms. Ask transcripts reuse the layout of messages that did not change, so a 5,000-message conversation stays responsive while a reply streams, and at most 10,000 messages are kept in memory (older ones come back with "Load earlier messages"). Logs keep the last 20,000 lines. See `docs/TUI_PERFORMANCE.md` for the measurements and how to reproduce them.

## Telemetry

The TUI can export its own metrics and traces with the same pipeline and the same fields as the Admiral's telemetry (see [TELEMETRY.md](TELEMETRY.md)). It is off by default: with telemetry off, no exporter starts, no port opens, and the TUI and TUIKit instruments are switched off. Armada sends nothing to its authors; telemetry here means exporting to your own collector.

Turn it on in the `Telemetry` section of `~/.armada/tui.json` (or the file named by `ARMADA_TUI_PREFERENCES`):

```json
{
  "Telemetry": {
    "Enabled": true,
    "ServiceName": "armada-tui",
    "OtlpEndpoint": "http://127.0.0.1:4317",
    "PrometheusEnabled": false,
    "PrometheusPort": 9465,
    "LokiEndpoint": null
  }
}
```

| Field | Default | Description |
| --- | --- | --- |
| `Enabled` | `false` | Master switch. |
| `ServiceName` | `armada-tui` | Service name reported to the backend. Blank falls back to `armada-tui`. |
| `OtlpEndpoint` | `null` | OTLP collector endpoint. The usual choice, since a TUI session is short-lived. |
| `PrometheusEnabled` | `false` | Serve a Prometheus scrape endpoint while the TUI runs (`http://localhost:9465/metrics` by default). |
| `PrometheusPort` | `9465` | Scrape port, clamped to 1-65535. The default stays clear of the Admiral's 9464. |
| `LokiEndpoint` | `null` | Loki push endpoint. |

Settings are read when `armada tui` starts. The exporter subscribes to two meters and activity sources: `Armada.Tui` (below) and `TUIKit` (frame timing, input, commands, modals, and toasts; see TUIKit's `TELEMETRY.md`). In Prometheus the TUI's series are:

| Prometheus series | Labels | Meaning |
| --- | --- | --- |
| `armada_tui_sessions_total` | none | TUI sessions started |
| `armada_tui_screen_views_total` | `route`, `screen` | Screens shown. `route` is the route pattern (for example `/missions/:id`), never a concrete id. |
| `armada_tui_commands_total` | `command`, `source`, `outcome` | Commands run. `source` is `key`, `palette`, `menu`, or `direct`; `outcome` is `ok` or `error`. |
| `armada_tui_approval_decisions_total` | `kind`, `decision` | Approval decisions (`approve`, `reject`, `deny`, `conditional`, `more_work`, `retry`, `stop`, `recall`, `restart`). |
| `armada_tui_approval_latency_seconds` | `kind`, `decision` | Histogram of the time from an approval reaching the TUI to your decision. |
| `armada_tui_ask_messages_total` | none | Ask Armada messages sent. |

Every command also opens an `armada.tui.command` span with the same labels. Labels never carry entity ids, titles, message text, or server URLs.

## Troubleshooting

Most problems are a wrong server address, a terminal setting, or a stale stored credential. Help, About Armada shows the TUI version, the server URL, the profile, the theme, the language, and which credential store is in use; start there.

### Cannot connect, or the wrong port

The header says `x Unreachable` or `o Offline`, or the login screen says "Failed to look up tenants." right after you enter your email.

- Check the Admiral answers: `curl http://127.0.0.1:7890/api/v1/status/health` (use your server's URL). If that fails, the server is not running or not reachable from this machine.
- Point the TUI at the REST port (`admiralPort`, 7890 by default), not the MCP port (`mcpPort`, 7891 by default). The MCP port answers MCP clients only, so the TUI fails there.
- Check the scheme: a server behind TLS needs `https://`. `--server URL` connects and saves a profile; in the login screen's Server picker, `e` edits the highlighted server's name and URL. `ARMADA_URL` overrides the server for one run.
- `Live` in the header means the WebSocket is connected. `Healthy` with `Offline` means REST works but the WebSocket does not (a proxy that does not pass WebSocket upgrades, for example); lists still load and refresh on their timers, but live updates and toasts wait until it reconnects (the TUI retries with backoff from 1 to 30 seconds).
- Through Armada.Proxy, use the proxy's URL; File has Switch Deployment and Proxy Logout.

### Ask says the captain is not connected over MCP

Ask shows "This captain is not connected to Armada over MCP, so it can answer but cannot propose actions." The captain can chat, but dispatches and other actions need it to reach the Admiral's MCP endpoint. Common causes:

- The captain's MCP configuration points at a different host or port than the Admiral listens on. The MCP listener only answers requests whose Host matches the Admiral's `rest.hostname`: an Admiral bound to `127.0.0.1` rejects `http://localhost:7891/mcp`, and the reverse. Run `armada mcp install` again after changing the hostname or ports, so the client entries match (the Settings Server tab shows the MCP port).
- The captain runs on another machine (a Harbor, a container) that cannot reach the Admiral's MCP port.
- The connection goes through Armada.Proxy, which does not relay MCP.

The note links to the setup instructions for the captain's runtime. Quick actions (`/dispatch`, `/status`, and the rest) work without MCP.

### Login problems

- "No tenants found for this email.": the email has no account on this server; check the server in the Server picker.
- "Authentication failed.": wrong password, or the account is inactive. A fresh install uses `admin@armada` / `password`.
- "API key authentication failed.": press `F2` for API Key Login and paste a session token, a credential's bearer token, or the Admiral API key. The TUI tries each form and checks it with `whoami`.
- "Your session expired. Sign in again.": the stored token is no longer valid (expired, revoked, or the server's data was reset). Sign in again; File, Sign out forgets a stored token without signing in.
- `ARMADA_TOKEN` skips the login screen only when the server accepts the token; otherwise the login screen opens.

### Terminal too small

The TUI needs at least 80 columns by 24 rows. Below that it shows "Terminal too small" with the size it needs and the size it has, and continues as soon as the window is large enough (`Ctrl+Q` still quits). At 80x24 the sidebar is hidden (`Ctrl+B` shows it over the screen); from 110 columns it is shown in full. Enlarge the window or reduce the font size; in tmux, a small pane or a smaller client attached to the same session limits the size.

### Broken borders, question marks, or boxes instead of lines

The terminal is not drawing the Unicode line and symbol characters. Choose View, Icons: ASCII (saved in `tui.json`), which writes only ASCII for borders, icons, and charts. Auto picks ASCII when the terminal does not look like UTF-8: `TERM=dumb`, a `LC_ALL`, `LC_CTYPE`, or `LANG` value without UTF-8 (such as `C` or `POSIX`), or legacy conhost on Windows. If the terminal does support UTF-8 but your locale says otherwise, set a UTF-8 locale (for example `LANG=en_US.UTF-8`) instead. Over SSH, make sure the locale reaches the server side (`SendEnv LANG LC_*` in the client config and `AcceptEnv` on the server, or export `LANG` in the remote shell); with no locale variables at all the TUI assumes UTF-8.

### Colors

When `NO_COLOR` is set, Theme: Auto picks High contrast, which uses reverse video and underline for selection and focus and ASCII borders, so it reads without color. Pick a theme in View to override Auto; the choice is saved. Auto reads the terminal background from `COLORFGBG` and otherwise assumes a dark background, so on a light terminal that does not set `COLORFGBG`, choose Theme: Light. No state depends on color alone.

### SSH and tmux

- Run the TUI on either side of SSH: locally with `--server` pointing at the remote Admiral (through an SSH tunnel such as `ssh -L 7890:127.0.0.1:7890 host` when the port is not exposed), or on the remote host inside your SSH session.
- tmux: use a 256-color terminal type (`set -g default-terminal "tmux-256color"` or `"screen-256color"`). tmux waits after Esc to see whether a key sequence follows; set `set -sg escape-time 10` so Esc and Alt+arrow keys respond at once.
- Copying uses OSC 52. In tmux, `set -g set-clipboard on` lets it reach your local clipboard; terminals without OSC 52 get a dialog with the text to select by hand.
- `F12` hands the mouse back to the terminal so you can select text with it; press `F12` again to give it back to the TUI.
- Over SSH the macOS Keychain is often locked; the TUI then falls back to the file credential store (below).

### Keychain and credential store

Tokens are kept in the macOS Keychain, Windows Credential Manager, or libsecret (`secret-tool`), and in `~/.armada/tui-credentials.json` (mode 0600) when none of those works. If the keychain prompts on every start, is locked (SSH, headless sessions), or `secret-tool` is not installed, use the file store: `ARMADA_TUI_CREDENTIAL_STORE=file`. `ARMADA_TUI_CREDENTIALS` moves that file. To forget a stored token, use File, Sign out, or delete the entry for the profile (or the file).

### Where the TUI keeps its files

| File | Contents |
|---|---|
| `~/.armada/tui.json` | Preferences: profiles, theme, icons, language, layout, last route, table columns and page sizes, refresh intervals, notification settings, key bindings, telemetry. Never a secret. `ARMADA_TUI_PREFERENCES` moves it. |
| `~/.armada/tui-credentials.json` | Tokens, only when the file credential store is in use. `ARMADA_TUI_CREDENTIALS` moves it. |
| `~/.armada/tui-notifications.json` | The last 100 notifications. |
| `~/.armada/tui-activity-views.json` | Saved views on the All Activity screen. |

`~/.armada` is the Armada data directory; `ARMADA_DATA_DIR` moves it. The TUI writes no log file of its own (it owns the terminal while it runs); the server's logs are in the server's data directory, under `logs`. Exports, backups, and snapshots go to the folder you start the TUI from unless you type another path, or to `ARMADA_TUI_SAVE_DIR` when it is set.

### Resetting preferences

Quit the TUI and delete or rename `tui.json` (or point `ARMADA_TUI_PREFERENCES` at a new file); the next start uses the defaults and recreates the default profile for the local Admiral. Stored tokens are kept separately (per profile name and URL), so you usually stay signed in. A `tui.json` that cannot be read is moved aside to `tui.json.bak` and the defaults are used. To undo only a key rebinding, remove its entry from `KeyBindings`.

### Performance and CPU

An idle TUI uses about 1 percent of one core. If it uses more, check for screens with a short auto-refresh interval (the interval is in the screen's top right; View, Auto-refresh interval... changes it, and Off makes it `manual`), a very long Ask conversation that is streaming, or a slow server (every refresh waits on it). `docs/TUI_PERFORMANCE.md` has the measurements and how to reproduce them.

### Ctrl+Q does not quit

`Ctrl+Q` quits from any screen, but an open dialog or picker takes every key first; press `Esc` to close it, then `Ctrl+Q`. File, Quit does the same from the menu.

### Reporting a bug

Help, Save screen snapshot... writes what the screen shows, as plain text at the terminal's size, to a file you choose (the text is taken before the save prompt opens). Attach it to the report together with Help, About Armada (TUI version, server, theme, credential store), `armada --version`, your terminal and operating system, `TERM`, `LANG`, and the terminal size, and the keys you pressed. A snapshot contains whatever was on screen, such as entity names, emails, and paths, so read it before you share it.
